# 第一部分 · 这个产品是什么

## 1.1 一句话

**一台小盒子，插进客户的网络里，自己把网络摸清楚，然后告诉客户：你有哪些设备、连得好不好、哪里有问题、建议怎么改。**

## 1.2 它解决什么问题

用我们真实做过的一次诊断举例。

客户的网络里装了摄像头，老是卡。原来的做法是：工程师带着笔记本上门，用一堆零散的命令行工具手工排查，花半天，最后得出一个结论，写个报告，人走了以后就没人再管了。

我们那次排查发现的实际情况是：

- 网络里有 **29 台设备**，其中 9 台是智能开关、2 台是摄像头、1 台是录像服务器、还有电视和门铃
- 摄像头卡的原因是：它用的是无线，而那台无线设备所在的那个频段，周围有 **8 个邻居的路由器** 在抢，信道占用率到了 45%~80%
- 同一台交换机上另一个**有线**的摄像头，延迟只有 2.7 毫秒，完全不卡
- 对比之下，无线那两个摄像头延迟抖动 31 毫秒、丢包 5%

这些结论，靠人手工排查要半天。这个产品要做的是：**盒子插上去 15 分钟自动得出同样的结论**，而且此后每天、每周自动重新检查，出报告，有问题自动报警。

## 1.3 覆盖哪几类设备

| 类别 | 要管什么 |
|---|---|
| 有线网络 | 交换机、路由器、网线链路 |
| 无线网络 | 路由器/无线接入点、信道、信号强弱、有多少设备连着 |
| 摄像头与录像机 | 画面卡不卡、录像有没有断层、硬盘还够不够 |
| 门禁 | 在线状态、刷卡记录有没有正常上报 |
| 智能设备 | 智能开关、传感器、电视这些联网小设备 |

# 第二部分 · 整体长什么样

```
                    ┌──────────────────────┐
                    │   网页界面（人看）      │
                    └───────────┬──────────┘
                                │
                    ┌───────────▼──────────┐
                    │  后端服务（管数据、派活）│
                    └──┬────────┬────────┬─┘
                       │        │        │
        ┌──────────────▼──┐  ┌──▼─────┐  ┌▼──────────────┐
        │ 业务数据库        │  │ 指标库  │  │ 消息邮局        │
        │ (设备/问题/报告)   │  │(延迟等) │  │ (各部分传话)    │
        └─────────────────┘  └────────┘  └┬─────────────┬┘
                                          │             │
                        ┌─────────────────▼──┐   ┌──────▼─────────────┐
                        │ 采集器（不问 AI）     │   │ AI 助手（要动脑时才出场）│
                        │ 定时主动扫网络        │   │ 能查、能写新工具       │
                        │ 只读，不改任何配置     │   │ 只读，不改任何配置     │
                        └────────────────────┘   └────────────────────┘
                                   ↑                      ↑
                                   └──── 物理网线 ─────────┘
                                      （插在客户网络里）
```

**读这张图的三个要点：**

1. **采集器和 AI 助手是两条独立的路。** 日常巡查由采集器干，不花钱、不慢、不依赖外网。只有需要"动脑子"的时候才叫 AI。
2. **AI 助手在最后面，不是必经之路。** 网页上的图表、设备列表、延迟曲线，全都是直接读数据库画出来的，不经过 AI。所以页面快，而且 AI 挂掉了页面照样能用。
3. **采集器和 AI 助手都不许改配置。** 它们只能看、只能测。改配置是后面阶段由人来决定的事。

# 第三部分 · 六个部件，各干什么

## 3.1 采集器

**通俗说：一个不睡觉的网管，每 5 分钟自己走一遍网络。**

| 项目 | 说明 |
|---|---|
| 干什么 | 找出网络里有哪些设备、每台设备开着哪些端口、是什么牌子、延迟多少、丢包多少、无线信号多强 |
| 怎么干 | 发广播包问"谁在线"、挨个地址 ping 一遍、试着连一下常见端口、读交换机和路由器的信息 |
| 频率 | 默认每 5 分钟一轮；关键指标（摄像头延迟）可以更频繁 |
| 不干什么 | 不改任何配置；不登录设备改东西 |
| 花钱吗 | 不花。它不问 AI，纯本地计算 |
| 技术 | Python 写；容器里给它开放物理网卡和发原始网络包的权限 |

**它每轮会先做一次自检**，这一步很重要。我们那次排查就踩过坑：这台电脑上装了 VirtualBox 虚拟网卡，系统把广播包从虚拟网卡发出去了，导致扫描网络时什么都没扫到（第一次探测返回 0 个设备）。改成明确指定"从真实网卡发出去"以后，立刻收到 19 个设备的回应。

所以采集器每轮都要检查：信号从哪块网卡出去、有没有发原始包的权限、无线网卡能不能用、网关是不是被运营商锁住了。检查结果直接显示在网页上。

## 3.2 AI 助手

**通俗说：一个能自己动手查、自己写小工具的工程师，只动眼不动手。**

| 项目 | 说明 |
|---|---|
| 干什么 | 回答"这台为什么卡"、分析故障原因、写报告、给出改进建议、写新的查询小工具 |
| 怎么干 | 用已经准备好的工具去查数据；工具不够用的时候，**自己写一个新的 Python 小工具，马上就能用** |
| 权限 | 可以随便扫描、随便发广播、随便拉视频流、随便写新工具；**不能改任何设备配置** |
| 花钱吗 | 花。每一次推理都要调用外部的大模型服务，按用量付费。所以要控制使用频率 |
| 技术 | 用 DeepSeek Harness 做引擎，装在独立容器里 |

为什么单独给它一个容器？因为它需要很高权限（发广播、扫描），但又绝对不能碰配置。把它关在盒子里，盒子上写着"只读"，比事后审计更可靠。

## 3.3 后端服务

**通俗说：网页的服务器。**

- 网页要什么数据，它从数据库里取出来给网页
- 网页上点了"分析这台设备"，它把活派给 AI 助手，然后一直汇报进度
- 管权限：谁能看什么、谁能操作什么
- 技术：Node.js

## 3.4 网页界面

**通俗说：人看的那个网站。**

- 是**独立做的**，不依赖 AI 助手那套引擎
- 所有图表、列表、拓扑图都是直接读数据库画出来的
- 每个页面上都挂一个对话框，可以随时问 AI
- 技术：React（前端框架）+ Three.js（做 3D 大屏）

## 3.5 任务工人

**通俗说：定时干杂活的。**

- 每天早 7 点生成日报，每周一生成周报
- 从消息邮局收采集器发来的数据，整理后存进数据库
- 检查有没有触发告警规则
- 把 AI 写的新工具从"临时区"搬到"正式区"（这一步需要人点确认）

## 3.6 三个存储

| 名字 | 大白话 | 存什么 | 为什么是它 |
|---|---|---|---|
| PostgreSQL | 业务账本 | 设备清单、连线关系、发现的问题、报告、操作记录 | 这些都是有相互关系的表格数据，它最擅长 |
| TDengine | 数值流水账 | 延迟、抖动、丢包率、信号强度、信道占用率 —— 所有带时间戳的数字 | 这类数据量极大且只追加不修改，专门为它设计的数据库，压缩好、查得快 |
| MQTT | 内部邮局 | 不是存数据，是传消息：采集器 → 后端、后端 → AI、告警通知 | 让各部分不用互相认识，发到邮局就行，谁需要谁去取 |

**为什么不用一个数据库全搞定？** 因为这两类数据的用法完全相反：设备清单经常要"按条件查、关联查"，数值流水账要"按时间段聚合、存海量"。硬塞进一个库，两边都别扭。

# 第四部分 · 数据怎么流动

## 4.1 日常巡查（不花钱的路）

```
第 1 步  采集器每 5 分钟醒一次
第 2 步  扫一遍网络，得到一批原始结果
第 3 步  整理成标准格式，发到消息邮局
第 4 步  任务工人从邮局取走，分类存进两个数据库
第 5 步  网页读数据库，画出设备列表和延迟曲线
```

全程没有 AI 参与。所以：不花钱、不受外网影响、断网也能跑。

## 4.2 需要动脑（花钱的路）

```
第 1 步  用户在网页上点中一台设备，问"这台为什么卡"
第 2 步  后端把"设备编号 + 当前在哪个页面"打包，交给 AI 助手
第 3 步  AI 助手开始查：
          · 调"看设备详情"工具 → 知道这是什么设备、连在哪
          · 调"看最近一小时数据"工具 → 看到延迟抖动 31 毫秒
          · 调"查历史问题"工具 → 没有相关记录
          · 对比同交换机上的有线设备 → 只有 2.7 毫秒
第 4 步  发现信息还不够：不知道它连在哪个无线设备、用的哪个信道
         现有工具里没有 → AI 自己写了一个 Python 小工具去查
         写完立刻运行，拿到结果
第 5 步  AI 给出结论 + 证据清单，返回给后端
第 6 步  后端存进数据库，网页显示出来
```

**关键点：AI 返回的结论必须带证据。** 每条结论后面都要列出"我是从哪个数据看出来的、原始数据在哪"。没有证据的结论，系统直接拒收。这样才能保证它不是瞎编。

# 第五部分 · AI 部分怎么工作（重点）

## 5.1 它能做什么、不能做什么

| 能做 | 不能做 |
|---|---|
| 扫描子网、发广播发现设备 | 改任何设备的配置 |
| 连接设备测试延迟、拉视频流测画质 | 重启设备 |
| 读取设备配置（有密码的情况下） | 改 Wi-Fi 信道 |
| 查数据库里的历史数据 | 改录像机设置 |
| **自己写新的 Python 工具并立刻使用** | 删除任何东西 |
| 分析原因、写报告、给建议 | |

这一版的边界很清楚：**AI 只动眼不动手。** 改配置这件事留给后面阶段，由人来决定和授权。

## 5.2 它能用的三种"手"

**第一种：现成的领域工具（最常用）**

我们预先做好一批工具，AI 直接调用。这些工具不是"ping 一下"这种小动作，而是打包好的完整能力：

| 工具名 | 干什么 |
|---|---|
| `probe_snapshot` | 给我某个网段过去一段时间的整体情况 |
| `device_detail` | 给我某台设备的完整档案：是什么、在哪、连到哪、能管到什么程度 |
| `device_config` | 给我某台设备的配置（需要密码，AI 看不到密码本身） |
| `cctv_health` | 给我某台摄像头的画面质量：码率稳不稳、有没有丢帧、打分多少 |
| `wifi_environment` | 给我某台无线设备周围的射频环境：信道占用、干扰、连着哪些设备 |
| `topology_query` | 谁能连到谁、路径是什么 |
| `findings_query` | 历史上发现过哪些问题 |

**为什么给"打包能力"而不是"裸命令"？** 如果直接给 AI 一个 `snmpwalk` 命令，它可能一次返回几万行文本，把 AI 的"记忆区"撑爆，而且每次都要重新拼参数。给它打包好的能力，一次调用就返回整理好的、有大小限制的结果。

**第二种：自己写代码连续调用（省时间省费用）**

普通方式是一问一答：AI 说"调工具A"，等结果，再说"调工具B"，再等结果……二十台设备就要来回四十次。

我们用的方式叫**程序化工具调用**：让 AI 直接写一段 Python 代码，在代码里连续调用：

```python
# AI 自己写出来的代码，一次跑完
设备列表 = 扫描子网("10.0.0.0/24")
有摄像头的 = [d for d in 设备列表 if 有端口(d, 554)]
结果 = {}
for d in 有摄像头的:
    结果[d] = 测视频延迟(d)
返回 汇总(结果)
```

一段代码解决，不用来回几十次。**又快又便宜。**

**第三种：自己造新工具（这是核心）**

碰到没见过的设备——比如客户家那台 H3C 的无线接入点——现成工具都不会用。这时 AI 会自己写一个：

```python
"""@tool
name: h3c_get_channel
description: 读取 H3C 无线接入点的 2.4G / 5G 信道
params:
  host: {type: string, required: true}
"""
import json, sys

def main(args):
    host = args["host"]
    # ... AI 自己写的查询逻辑 ...
    return {"ch2g": 1, "ch5g": 36}

if __name__ == "__main__":
    args = json.load(sys.stdin)
    print(json.dumps(main(args)))
```

写完存到指定目录，系统自动扫描并注册。**下一步它就能像调用现成工具一样调用这个新工具了**——不用重启、不用重新部署。

这个能力很重要，因为客户网络里什么牌子的设备都有，不可能预先写完所有厂家的对接代码。

## 5.3 工具脚本的写法约定

极其简单，一句话：

> **一个 Python 文件就是一个工具。参数用 JSON 格式从标准输入读进来，结果用 JSON 格式从标准输出打印出去。**

文件开头用注释写清楚名字、说明、参数格式，系统自动解析并注册。没有魔法、没有框架、不需要懂我们内部的任何东西。

## 5.4 AI 看不到密码

这是硬规定：

- **配置文件、代码、Git 仓库里，只写"密码存在第 3 号保险箱"，不写密码本身**
- 真正的密码存在本地加密存储里
- AI 说"我要读 10.0.0.204 这台设备的配置" → 由我们的工具拿着密码去连 → 只把配置内容返回给 AI
- **AI 从头到尾看不到密码原文**，操作日志里也不会出现密码

## 5.5 一次对话的完整例子

**用户在拓扑图上点中 `10.0.0.177` 这台摄像头，问："这台为什么卡？"**

```
后端 → AI：{ 设备编号: "E0:D3:62:B9:B9:87", 当前页面: "拓扑图" }

AI 调 device_detail
  → 得知：TP-Link 摄像头，无线连接，位置在书房

AI 调 probe_snapshot(过去1小时)
  → 得知：平均延迟 24.7 毫秒，抖动 18.8 毫秒，丢包 5%

AI 发现同网段还有一台有线摄像头，调 device_detail 对比
  → 得知：有线那台延迟 4.4 毫秒，抖动 2.7 毫秒，0 丢包

AI 判断：问题出在无线这一侧。但还需要知道它连在哪个无线设备上、用的哪个信道

AI 检查现有工具 → wifi_environment 需要无线设备的编号，但我们不知道它连的是哪台

AI 自己写了一个新工具 wifi_client_lookup.py，去查无线接入点的已连接设备表
AI 运行这个工具
  → 得知：连在 H3C 那台接入点上（10.0.0.204），2.4G 频段，信道 11

AI 调 wifi_environment(10.0.0.204)
  → 得知：信道 11 上有 8 个邻居路由器在抢，占用率 45%~80%

AI 给出结论：
  根本原因：摄像头连在 2.4G 信道 11 上，该信道被 8 个邻居路由器挤占，
           导致视频数据包排队重传，画面卡顿
  把握程度：82%
  证据：
    · 该摄像头抖动 18.8ms / 丢包 5% —— 来源：指标库，可点击查看曲线
    · 同交换机有线摄像头抖动 2.7ms / 0 丢包 —— 来源：指标库
    · 信道 11 有 8 个邻居 AP，占用率峰值 80% —— 来源：无线扫描记录
    · 该摄像头挂在 H3C 接入点的 2.4G 信道 11 —— 来源：新写的工具查询结果
  排除项：
    · 不是交换机或网线问题（网关延迟 0–3ms，抖动 0.4ms）
  建议（按优先级）：
    1. 把 H3C 接入点的 5G 信道从 36 改到 149 —— 风险：中 —— 操作手册：h3c-magic-ap
    2. 把该摄像头接入有线 —— 风险：低
```

网页上显示的就是这段话。每条证据都可以点击，跳回原始数据曲线。

# 第六部分 · 设备能管到什么程度

我们给每台设备定一个"可管理等级"。这是产品的核心指标——**它直接告诉客户：你的网络里有多少是看得见的，有多少是黑盒。**

| 等级 | 名字 | 什么条件 | 产品能干什么 |
|---|---|---|---|
| **L0** | 知道存在 | 扫描时它回应了 | 只能说"有这么台设备" |
| **L1** | 知道是什么 | 认出了品牌、型号、固件版本 | 显示档案、提示风险、给出默认端口 |
| **L2** | 读得到 | 有密码，能登进去读配置 | 保存配置快照、对比变化、发现配置漂移 |
| **L3** | 改得了 | 有密码 + 有授权 + 有对接脚本 | 执行变更（本阶段不做） |

**为什么这个分级重要？**

首页上最重要的数字不是"发现 29 台设备"，而是：

> **29 台设备中，6 台能读到配置，2 台能改，剩下 21 台还只是"知道存在"。**

客户一眼就能看出自己的网络有多"黑"。

# 第七部分 · 网页上有哪些页面

| 页面 | 内容 |
|---|---|
| **拓扑图** | 设备之间怎么连的，2D 图，可以拖动修正 |
| **3D 大屏** | 楼层立体图，设备在哪、状态如何（第一版只做"能定位"） |
| **设备列表** | 所有设备，可以筛选、排序、看治理等级 |
| **设备详情** | 单台设备的完整档案 + 历史曲线 + 操作手册入口 |
| **网络质量** | 延迟、抖动、丢包、信道占用的看板 |
| **问题列表** | 发现的问题，按严重程度排序，每条带证据 |
| **报告** | 日报、周报、故障分析报告 |
| **设置** | 扫描范围、授权、账号、密码保险箱、能力自检结果 |
| **对话框** | 每个页面右侧都挂一个，可以随时问 AI |

**对话框会带上"你正在看什么"**：在拓扑图上点中某台设备再问"它为什么卡"，AI 就知道你说的是哪台，不用你再解释一遍。

# 第八部分 · 客户配置和密码怎么管

## 8.1 一个客户一个 Git 仓库

每个客户在 GitHub 私有组织下有一个独立仓库（如果客户不允许数据出公网，就部署一个内网 Git 服务，配置一模一样）。

仓库里放：

```
客户仓库/
├── 站点信息.yml        楼层、房间、网段
├── 设备台账.yml        所有设备的档案（不含密码）
├── 期望拓扑.yml        应该怎么连（人工修正的拓扑图）
├── 扫描授权.yml        允许扫描哪些网段、有效期
├── 操作手册/           这个客户设备的手册
└── 报告/               历史报告
```

**仓库里绝对不放：** 明文密码、抓包原始数据、视频片段、客户个人信息。

## 8.2 密码怎么存

三层：

1. **加密存储**：真正的密码存在本地，用主密码加密
2. **只写引用名**：所有配置文件、代码、Git 仓库里，只写"密码在第 3 号保险箱"
3. **代理执行**：AI 和新工具都拿不到密码原文，只能提交"我要对某台设备做某个操作"，由专门的执行器拿着密码去连

好处：**改密码不用改任何配置文件，也不用重启。**

## 8.3 改动怎么走

人和 AI 提出的改动，都变成一个"提交申请"，在 Git 上走审核流程。谁提的、谁批准的、改了什么，全程有记录。

# 第九部分 · 怎么装，装在哪

## 9.1 硬件

| 方案 | 配置 | 适用 |
|---|---|---|
| **推荐** | 树莓派 5 / 8GB 内存 + **固态硬盘**（不要用 SD 卡，数据库写入会把卡写坏） | 单个客户、单个站点 |
| 稳妥 | x86 迷你主机 / 16GB | 设备多、要本地抓包分析 |
| 分离式 | 现场只放一个小采集盒，数据库和 AI 放在公司服务器 | 多个客户、多站点 |

## 9.2 装法

一条命令：

```
docker compose up -d
```

所有组件跑在容器里：采集器、AI 助手、后端、网页、任务工人、三个存储。每个容器是可以单独替换的。

## 9.3 首次使用流程

```
1. 盒子插上网线，开机
2. 用手机或电脑连上盒子的初始地址，打开网页
3. 勾选授权扫描的网段（这一步必须有，是合规要求）
4. 看自检结果：能不能发广播、无线网卡能不能用、信号从哪块网卡出去
5. 开始扫描，等 5–15 分钟
6. 网页上出现设备列表和图谱
7. 人工确认一下：哪些设备类型识别错了、哪条连线画错了（可以拖拽修正）
8. 对关键设备录入密码，治理等级从 L1 升到 L2
9. 连续采集 24–72 小时建立基线
10. 生成第一份《网络体检报告》
```

# 第十部分 · 分几步做

## 第 1 步 · 能看见（1 周）

**做出来什么**

- 采集器（用 Python 重写，替代现在那些零散脚本）
- 数据能存进数据库
- 网页上有两个页面：设备列表、网络质量

**怎么算做完了**

| 编号 | 验收条件 |
|---|---|
| A1 | 接入一个没见过的网络，**15 分钟内**网页上出现设备列表，覆盖实际设备的 90% 以上 |
| A2 | 一眼就能看出哪些设备是无线、哪些是有线（抖动差一个数量级） |
| A3 | 故意把虚拟网卡的优先级调高，自检要能报出"信号出口走错了"并给出修正命令 |

## 第 2 步 · 看得懂（1.5 周）

**做出来什么**

- 拓扑图（先做 2D）
- 设备详情页
- 可管理等级 L0–L3
- 问题规则引擎（阈值判断 + 同类对比）
- 3 份设备操作手册：H3C 接入点、Tapo 摄像头、海康摄像头

**怎么算做完了**

| 编号 | 验收条件 |
|---|---|
| B1 | 自动复现我们那次的结论：`.177` 抖动 31ms 对比 `.119` 抖动 2.7ms，自动生成"瓶颈在无线"的问题记录 |
| B2 | 设备详情页能回答"这台是谁、在哪、连到哪、能管到什么程度" |
| B3 | 问题记录里的每条证据都能点回原始数据 |

## 第 3 步 · 会对话（1.5 周）

**做出来什么**

- AI 助手接进来，能接受后端的任务
- 工具注册机制（AI 写的新工具自动生效）
- 7 个内置领域工具
- 每个页面挂上对话框
- **AI 自己造新工具的完整闭环**

**怎么算做完了**

| 编号 | 验收条件 |
|---|---|
| C1 | 在拓扑图上点中摄像头问"为什么卡"，返回带证据的结论，证据可点击回原始数据 |
| C2 | 让它做一个当前不存在的工具（比如查 H3C 接入点信道），文件出现在目录里，能力清单里工具数 +1，**下一个问题里它就能用这个新工具了** |
| C3 | 拔掉外网，基于本地数据的问题仍然能回答（日常功能不依赖外网） |

## 第 4 步 · 出报告（1 周）

**做出来什么**

- 日报、周报、故障分析报告三套模板
- 定时自动生成
- 存进数据库并推送到客户 Git 仓库

**怎么算做完了**

| 编号 | 验收条件 |
|---|---|
| D1 | 每天早 7 点自动出报告，不用人点 |
| D2 | 故障分析报告结构完整，**抽查任意 3 个数字都能在数据库里对上**（证明不是 AI 编的） |

# 第十一部分 · 为什么这么选

## 11.1 为什么 AI 引擎选 DeepSeek Harness

三条原因，都是硬功能：

**第一，它能"写代码连续调工具"。** 别的方式只能一问一答，二十台设备要来回四十次。它能写一段代码一次跑完——又快又省钱。

**第二，它能现场造工具并立刻使用。** 写完存到目录，下一步就能调用，不用重启。别的方式要么不能造，要么要重新部署。客户网络里设备牌子五花八门，这个能力是刚需。

**第三，它原生支持 DeepSeek 模型。** 我们用的是 DeepSeek 系列模型，不需要额外适配。

## 11.2 为什么网页自己独立做

因为**页面渲染直接读数据库，不经过 AI**。这样：

- 页面快（不用等 AI）
- 省钱（看图不花 AI 的钱）
- AI 引擎换了，网页一行都不用改

## 11.3 为什么用三个存储

前面第四部分讲过：业务数据和数值流水账的用法完全相反，硬塞一个库两边都别扭。消息邮局则是为了让各部分不用互相认识。

## 11.4 为什么用 Docker

- 树莓派、迷你主机、笔记本上跑的是同一套东西
- 升级只换一个容器，不影响别的
- 每个组件是独立盒子，出了问题好定位

## 11.5 为什么 AI 和采集器分开

采集器每 5 分钟跑一次，如果每次都要问 AI，费用会高得离谱，而且会慢。分开之后：

- 采集器：高频、免费、不依赖外网
- AI：低频、按需、有价值的深度分析

# 第十二部分 · 名词对照表

我之前用了很多行话，这里统一翻译：

| 我之前说的 | 大白话 | 在这个系统里指什么 |
|---|---|---|
| harness | AI 引擎 | 让 AI 能调工具、写代码、干活的那套程序 |
| 探针 / probe | 采集器 | 定时扫网络、收集数据的那部分 |
| 数据面 / 控制面 | 干活的 / 动脑的 | 采集存数据 vs AI 分析 |
| fact / 事实 | 采集结果 | 采集器扫出来的原始结论 |
| finding | 问题记录 | 系统发现的异常 |
| adapter / 适配器 | 对接脚本 | 针对某个品牌设备写的专用工具 |
| Runbook | 操作手册 | 教你在这台设备上怎么改设置 |
| MQTT | 消息邮局 | 各部分之间传消息的中间件 |
| schema | 数据格式定义 | 规定数据长什么样 |
| PTC / 程序化工具调用 | 写代码连续调工具 | AI 写一段代码一次调用多个工具 |
| profile | 配置档案 | AI 引擎的一份配置，决定它有哪些能力 |
| token | 计费单位 | AI 按处理的文字量收费 |
| GitOps | 配置走提交审核 | 所有改动变成提交申请，审核后生效 |
| 治理等级 L0–L3 | 可管理程度 | 从"知道存在"到"能改配置"四级 |
| egress interface | 信号出口网卡 | 数据包从哪块网卡发出去 |
| host 网络 | 直连物理网卡 | 容器不做网络隔离，直接用真实网卡 |
| SSE / WebSocket | 服务器推送通道 | 服务器持续把进度推给网页 |
| 子代理 | 分身 | 让 AI 同时派几个自己分头干活 |
| 基线 | 正常水平 | 平时正常时的数值范围，用来判断异常 |
