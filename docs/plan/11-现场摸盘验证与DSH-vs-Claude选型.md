## 4. 关键发现 → 对探针设计的验证（02 文档对照）

| # | 实测发现 | 对探针设计的含义 |
| --- | --- | --- |
| 1 | **多协议交叉验证有效**：ping 活 26 台，另有 3 台（.33/.105/.111）ping 不响应但 ARP 可见 | 验证「ICMP + ARP 双通道」必要性；探针必须**以 ARP/CAM 为准、ping 为辅**，否则漏设备 |
| 2 | **NetBIOS 全部超时**（nbtstat 无响应） | 现代网络 NetBIOS 已死 → 探针用 **mDNS + OUI + 端口特征**命名设备，符合 02 §4 设计 |
| 3 | **554(RTSP) + 443 开 = 摄像头**，一次端口探测即识别 3 台 TP-Link 摄像头 | 验证「低速率端口探测 + 端口特征推断设备类型」可用；Hikvision 单靠 OUI 就能定位 |
| 4 | **2 台设备用随机 MAC**（本地管理位） | 探针需识别并标注「隐私地址」设备，勿因 MAC 变化误报「新设备上线」 |
| 5 | 网关 80/443 开、SSID/WPA3/信道信息可从客户端侧拿到 | 探针从「客户端视角」也能摸到不少信息，不依赖交换机凭据即可出首屏拓扑 |
| 6 | **没有企业级交换机可见（或 .204 H3C 是 AP）**，端口级拓扑拿不到 | 说明在无 SNMP 凭据环境下拓扑只能到「L2 邻居 + 类型推断」层级；LLDP/CAM 是 Pi 端下一步（02 §4.2） |
| 7 | 全程零写入、无 Agent、无凭据 | 验证「透明信任」卖点可实现：只读协议足够输出有商业价值的报告 |

## 5. 探针实现选型：DSH 还是 Claude？

### 5.1 决策矩阵

| 维度 | **DSH（DeepSeek Harness）** | **Claude Code + Python FastMCP** |
| --- | --- | --- |
| 现场 7×24 常驻 | ✅ **直接跑树莓派**（Node 20+ ARM64）；agent 大脑+工具+看板**单栈单进程**，systemd 自启自愈 | ⚠️ Claude Code 无头跑 Pi 别扭；通常 agent 在笔记本、Pi 只跑 MCP server → **多一跳网络**（正是原文自己担心的防火墙穿透难题） |
| 「透明大屏」看板 | ✅ **DSH Web GUI（本地 3080 端口）就是看板**：探针做成 Client 插件挂 Slot，HDMI kiosk 全屏即交付物 | ❌ 需另建 Web 应用 |
| 协议库生态 | ⚠️ 需 child_process 调 `arp-scan/snmpget/ffprobe` 或 Node 包（可行，工具都是 CLI） | ✅ Python 生态最强（pysnmp / scapy / onvif / ffmpeg） |
| 成本 | ✅ deepseek 按 token 便宜；关键巡检**可纯规则跑（不烧 token）**，LLM 仅用于报告/小贴士，可接本地 Ollama 全离线 | ⚠️ Claude API 按 token，7×24 循环成本累积；无同等级本地模型 |
| 「零数据上云」 | ✅ 可全本地（本地模型或规则模式） | ⚠️ 强依赖云 API（除非笔记本侧代理） |
| 开发效率 | ✅ 单语言（JS）+ 插件框架自带工具注册/生命周期/UI | ⚠️ 两套栈 + MCP 协议胶水 + SSE 鉴权/NAT 穿透 |
| 开放性/未来 | ⚠️ 生态较新 | ✅ MCP 开放标准，可插任意 agent |
| 本会话实证 | ✅ **本次摸盘就是 DSH agent 多工具闭环的实证**（采集→OUI→交叉验证→后台任务→报告），且自动处理了 PS5.1 兼容性错误 | ❌ 未实证 |

### 5.2 推荐：混合架构（DSH 探针 + FastMCP 驱动层，双路线兼容）

```
                树莓派小黑盒（现场）
   ┌───────────────────────────────────────────────┐
   │  DSH 实例（Node 20 LTS，systemd 托管）          │
   │  ├─ Host 插件：发现/诊断/自愈/报告 Tools        │
   │  ├─ Client 插件：大屏看板（DSH Web GUI，kiosk）  │
   │  └─ agent 循环：规则巡检为主 + LLM 报告为辅      │
   │        │ (localhost MCP client)                │
   │        ▼                                       │
   │  Python FastMCP 驱动进程（独立子进程）           │
   │  arp_discovery / snmp_query / inspect_rtsp /    │
   │  topology_build / health_report / self_heal     │
   └───────────────────────────────────────────────┘
         ▲                                           
         │ 未来可选：同套 MCP Server 暴露给开发机     
   ┌─────┴────────────┐                              
   │ Claude Code（开发机）│ ← 仅作外置顾问/疑难二次意见  
   └──────────────────┘                              
```

**为什么这样定：**
1. 探针的本质需求 = **单机自包含、7×24 无人值守、本地大屏、零上云、低成本** → DSH 一条龙满足，且省掉「agent↔MCP 服务器」跨网络一跳（原文架构的最大脆弱点）。
2. **驱动层用 Python FastMCP 保留**：Python 的协议生态（SNMP/ONVIF/ffmpeg）最全，且 MCP 是开放标准 → 将来想切回 Claude Code 远程驱动同一个探针，驱动层**零改动**。两条路线共享同一驱动层，**选型不烧钱**。
3. **LLM 用量收敛**：巡检/自愈用确定性规则（不烧 token）；LLM 只写报告与「AI 小贴士」→ 无论 DSH 还是 Claude，成本都受控；隐私敏感客户可关掉 LLM 或换本地 Ollama。
4. 本次摸盘本身就是 DSH agent 闭环的证据：多工具调用、错误恢复、结构化输出、Markdown 报告 —— 正是探针 24×7 要复刻的行为。

### 5.3 分工建议（最终）

| 层 | 用什么 | 谁写 |
| --- | --- | --- |
| 探针运行时（agent + 工具 + 看板） | **DSH**（探针 preset/插件） | 外包开发 + 本会话可先行打样 |
| 物理驱动层（FastMCP Server） | **Python**（FastMCP，7 个工具见 02 §7） | 外包开发 |
| 疑难诊断二次意见 / 复杂报告润色 | **Claude Code**（开发机，可选） | 创始人按需 |
| 大屏交付物 | DSH Web GUI（Client 插件 Slot） | 外包开发 |
