# BuildingOS Contract Philosophy

> A decision memorandum for the team: all **21 decisions** from the M0 phase, explained in plain language.
> This is not a technical specification — it records *why* we chose what we chose. For details, see the [Decision Index](#11-decision-index).

---

## 0. Three sentences that frame the product philosophy

1. **We do not build engines; we operate them.** We adopt existing harnesses (DSH, Codex) and build the layer above them: governance, documents, and interfaces.
2. **The system is documents — not a single line of code.** Application behavior (rules), capabilities (skills), persona (prompts), and runtime parameters (configs) are all Markdown / YAML files governed by Git — reviewed, versioned, and rolled back like code.
3. **Engines are swappable; the API and the governance model are not.** Whether you run DSH today or Codex tomorrow, the team sees the same system. That is the *stable boundary*.

## 2. Skills (5 decisions)

**D1. A skill is a directory.** `<skill-name>/SKILL.md`. Single `.md` files imported from other systems are automatically wrapped into a directory bundle during import.
> Why: Codex only recognizes directory bundles. Supporting two shapes would double the compilation logic and clutter the repository. One canonical shape, automatic conversion on import.
> Trade-off: one extra packaging step — performed by the machine, invisible to the user.

**D2. Capabilities an engine lacks still travel with the document.** Codex supports *implicit invocation* (running a skill's script is recognized as invoking that skill); DSH does not. The switch is inert on DSH but is carried inside the `metadata` namespace during compilation, so round-trips never lose it.
> Why: one document serves both engines. If we dropped the field, re-importing from DSH would lose the setting permanently.
> In short: we cannot grant the capability, but we will not lose the information.

**D3. Tools are registered once; skills file a requisition.** How a tool connects (address, protocol, authorization) is written exactly once per tenant (`runtime.yaml`). A skill merely declares "I need `telemetry`." The compiler fills in the connection details.
> Why: two skills using the same tool, each carrying its own connection spec, means fixing one place and forgetting the other — conflict. One registration record per tenant, the way a single personnel file lives in HR.
> CI backstop: a requisition naming a tool that is not in the registry fails the PR.

**D4. A skill's "business card" gets its own slot.** Display name, icon, colors, and default prompt live in a dedicated `ui:` block.
> Why: buried inside a free-form field, a future dynamic UI could not reliably distinguish "this is the card" from "a random note." A dedicated slot establishes the rule now; the M3 dynamic UI reads directly from it.

**D5. Tenant data and skill resources are declared separately.** Skill-owned files (documentation) use `references:`; tenant-owned data (topology files) use `data:`.
> Why: both are "references," but they differ in nature — one is part of the skill (travels with it), the other is a tenant asset (merely used by the skill). Separating them makes dependencies auditable and gives dynamic context assembly a basis.

## 3. Rules (4 decisions)

**D6. Hard-rule permissions are generated by the rule itself.** The rule's Markdown carries a machine-readable permission fragment; the compiler derives the `runtime.yaml` permission table from it.
> Why: the rule says "no data exfiltration" while the permission table enforces actual allow/deny — two sources describing the same constraint will drift. When rules generate permissions, drift is structurally impossible.
> In short: the rule is the law; the permission table is the law's automatically generated enforcement list. You never hand-write a second copy.

**D7. One rule file may contain multiple sections.** Importing from Codex's AGENTS.md naturally produces "one file, many sections."
> Why: forcing one rule per file would explode a large ruleset into dozens of files.
> Ordering: sections follow in-file order; files are ordered by their `order` value.

**D8. Role-scoped rules are reserved, not implemented.** The `applies-to` field stays in the schema; the compiler ignores it for now.
> Why: multi-role (ops assistant vs. sales assistant) is a real need, but the "role" concept is not yet defined at the product level (M5 wizard). Keep the field so no data is lost; implement when the concept lands — together with role-based persona selection.

**D9. The boundary between rules and prompts: is violating it a bug or a style choice?** When the model violates this line, is your first reaction "that's a bug" or "that's off-style"? Bug → rules (must be enforced); style → prompts (negotiable).
> Why: this prevents "replies must be concise" from being hardened into a rule, and prevents "no data exfiltration" from being treated as a tone preference.

## 4. Prompts (3 decisions)

**D10. Multiple personas merge into one.** Several persona files in the repository? In M0 they are concatenated into a single persona in `order` sequence.
> Why: role-based persona selection is M5 (together with D8). For now they merge; conflicts are settled in review, and lint warns that a merge will occur.

**D11. Language is for machines; tone is for models.** `language` (zh-CN / en) is a structured field the machine can consume (mapped to the engine's language setting); `tone` (professional, concise) is simply part of the prompt text.
> Why: language affects configuration (machine-owned), tone affects expression (model-owned). Each in its place.

**D12. Persona is injected at session level.** After compilation it lands in Codex's developer instructions and DSH's persona section — "this session's persona."
> Why: Codex also exposes model-level personalities (friendly / pragmatic presets). Those belong to the model vendor; tenants should not override engine-bundled templates. We own only the session level.

## 5. Runtime parameters (4 decisions)

**D13. One shared vocabulary for sandbox and approval.** Read-only / workspace-write / danger-full-access; never / on-request / unless-trusted.
> Why: the same names as Codex (one less translation layer), mappable to DSH knobs, and "read-only by default" is precisely the product position.

**D14. No exception channel for permissions.** `runtime.yaml` forbids hand-written permission sections; CI rejects them outright.
> Why: an exception channel reopens dual-write drift. Temporary access? Write a temporary rule through a PR — auditable and rollback-able, cleaner than an exception.
> In short: all permissions are rules; there is no back door.

**D15. Memory services are placeholder declarations for now.** `memory: { provider: ... }` only states which kind of memory; details (address, scope) await M1 research.
> Why: Codex ships native memory (MEMORY.md) while DSH uses MCP memory servers — the differences are not fully researched yet (Appendix A.7.3). Defining fields now would be guessing. Placeholders do not guess.

**D21. Configuration is split into three layers; keys never enter the repository.** Bootstrap configuration (local engine/model selection and credential entry) → document configuration (`runtime.yaml` in Git: engine, model, parameters) → secret configuration (tokens/credentials, injected via environment, **never in Git**).
> Why: writing model tokens and Git credentials into `runtime.yaml` is hanging the keys on the front door — visible in PR reviews, permanent in history, and fatal to the governance model (the same principle as D14: no exceptions).
> In short: configuration may live in the repository; keys never do.

## 6. Document assembly (1 decision)

**D20. Order across families uses a single ruler.** `order` in rules and prompts is one **global numbering space** — a single sequence for the whole document set. Cross-family numeric conflicts (e.g., two rules and a persona all at 20) are rejected by lint; no ambiguity is left to guesswork.
> Why: when compiling to engine views (AGENTS.md / system-prompt), every document must line up in one sequence. Two numbering spaces would mean guessing — or inventing new rules — at merge time. One ruler: conflicts error out, ordering is always deterministic.
> In short: the whole repository queues by a single sequence number; duplicates error out.

## 7. Tenancy model and data boundaries (4 decisions)

**D16. Data lives in three layers and never mixes.** The Git repository holds the application's source of truth (shared); the runtime state store holds users' private state (conversations, memory, preferences — isolated per session); business data stays in the existing systems (accessed through tools, with user-level authorization).
> Why: putting user data into the Git repository means repository bloat plus mixing source code with runtime data — Git governance collapses.
> In short: the repository holds the brain, the state store holds the private, business data stays where it lives.

**D17. Skills layer on top of each other.** Platform-bundled packs → industry template packs (M4) → tenant-owned skills; same-name nearest-wins. Multiple products = multiple tenant repositories.
> Why: one skill set per product is the default, but "template + customization" is a real need — DSH's layered registry is the proven model (nearest wins).

**D18. Tools have four states: use, select, designate, install.** Use is native (engines are MCP clients); selection is bounded (registered ∩ permitted); designation goes through the skill reference (registration still lives in `runtime.yaml`); **installation must go through a PR** (the AI proposes → review → takes effect). No runtime installation.
> Why: a new tool is a new permission surface. Auto-install sounds convenient, but it lets the AI grant itself permissions — it must pass a PR (an extension of D14).

**D19. The repository holds not only the brain but the world model.** The repository = behavior documents (rules/skills/prompts/configs) + world-knowledge documents (documents such as `network.md` produced by harness analysis). Judgment: **worth human review, subject to human edit, version-significant → Git; transient, high-frequency, not worth review → DB**. toB: `knowledge/` in the tenant repository; toC: `users/<uid>/` in the product repository (degrade to the storage layer when user counts grow too large). Knowledge documents stay free-form; their schema awaits M1 validation.
> Why: a network-maintenance AI's `network.md` is "what this world looks like" — generated by the harness, reviewed by humans, versioned like code. MIS transactions are transient state and belong in the DB.
> In short: the brain goes into the repository, the world model goes into the repository, transaction data stays in the DB.

## 8. Three principles that run through every decision

1. **Single source of truth.** The same fact is written once. Tool registration (one `runtime.yaml`), permissions (generated by rules), persona (merged into one).
2. **No information loss.** What an engine cannot do is still carried in metadata (D2, D4, D8).
3. **Machine-verifiable.** Every low-level mistake — referencing a nonexistent tool, a malformed color, hand-written permissions — is caught by CI, not by memory.

---

## 9. Three tests to ask when writing documents

1. Violating it — **bug or style preference?** → rules or prompts (D9)
2. **Registration or reference?** → `runtime.yaml` or skill dependency (D3)
3. Does the engine support it? If not, **no capability, but carry the information** (D2, D4, D8)
