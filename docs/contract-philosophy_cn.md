# BuildingOS 契约哲学

> 写给自己的决策备忘录：M0 阶段 **21 个决策**，全部用大白话讲清楚。
> 这不是技术规格，是"我们为什么这么定"。想查细节，见文末《决策出处》。

---

## 0. 先记住三句话（整个产品的哲学）

1. **我们不造发动机，我们运营发动机。** 引擎用现成的（DSH、Codex），我们做引擎之上的那层：治理、文档、界面。
2. **系统全是文档，一句代码都没有。** 应用的行为（规则）、能力（技能）、人格（提示词）、运行参数（配置）全是 Markdown / YAML 文件，走 Git 评审、版本、回滚。
3. **引擎可以换，API 和治理不变。** 今天用 DSH、明天换 Codex，团队看到的还是同一套东西——这就是"稳定边界"。

---

## 1. 这 20 个决策是什么

M0 阶段我们把"租户仓库里那些文档长什么样"定死了。四个文档家族：

| 家族 | 回答什么问题 | 决策数 |
|---|---|---|
| skills（技能） | 怎么干活 | 5 |
| rules（规则） | 什么不能干 | 4 |
| prompts（人格） | 用什么语气干 | 3 |
| configs（参数） | 用什么工具干 + 配置怎么分层 | 4 |
| 租户模型 | 数据怎么隔离、技能怎么分层、世界知识放哪 | 4 |
| 装配顺序 | 跨家族文档怎么排序 | 1 |

---

## 2. 技能（5 条）

**D1. 技能必须是一个文件夹。** `<技能名>/SKILL.md`。从别的系统拿来的单个 `.md` 文件，导入时系统自动帮你打包成文件夹。
> 为什么：Codex 只认文件夹。两种形态并存 = 编译逻辑写两遍、仓库乱。统一一种，导入自动转换。
> 代价：多一层"打包"动作——机器做，人无感。

**D2. 引擎没有的能力，信息也要带着走。** Codex 有"隐式触发"（跑个脚本就自动认出在用什么技能），DSH 没有。这个开关在 DSH 上不生效，但编译时藏在 metadata 的角落里带着，来回导不丢。
> 为什么：文档是"一份、两引擎共用"。丢了，哪天从 DSH 导回来就永久丢设置。
> 人话：**能力给不了，但信息不丢。**

**D3. 工具注册只写一份，技能只填申请单。** 工具怎么连（地址、协议、授权）全租户只写一份（runtime.yaml），技能里只写"我要用 telemetry"。编译时自动补全。
> 为什么：两个技能用同一个工具，各写一份说明书 → 改一处忘一处 → 打架。像公司人事档案统一在 HR。
> CI 兜底：申请单上写的工具名，户口本里查不到 → PR 不通过。

**D4. 技能的"名片"单独放一格。** 显示名、图标、颜色、默认提示语放专门的 `ui:` 块。
> 为什么：塞在开放字段里，将来做动态界面时没法可靠区分"这是名片"还是"随手写的备注"。单独一格 = 规矩先立好，M3 的动态 UI 直接从这里取数。

**D5. 租户数据和技能资源分开声明。** 技能自带的文件（说明书）用 `references:`，租户的数据（拓扑文件）用 `data:`。
> 为什么：都是"引用"，但性质不同——一个是技能的一部分（跟着技能走），一个是租户的资产（只是被技能用）。分开了，依赖可审计、动态上下文构建有依据。

## 3. 规则（4 条）

**D6. 硬规则的权限，由规则自己生成。** 写规则的 Markdown 里带一个机器可读的权限片段，编译时自动生成 runtime.yaml 的权限表。
> 为什么：规则写"禁止数据外泄"，权限表管"实际放行"——两个地方描述同一件事必然漂移。规则生成权限 = 单一事实源，漂移在构造上不可能。
> 人话：规则是"法律"，权限表是"法律自动生成的执行清单"——不让你手写第二份。

**D7. 一个规则文件可以装多段。** 从 Codex 的 AGENTS.md 导进来时，天然就是"一个文件多个章节"。
> 为什么：强行一文件一条，几十条规则就几十个文件，爆炸。
> 排序规则：段落按文件内顺序，文件之间按 order 排序。

**D8. "按角色生效"的规则，先留着不做。** `applies-to` 字段先占着，编译时忽略。
> 为什么：多角色（运维助手 / 销售助手）是真实需求，但"角色"概念在产品里还没定义（M5 向导）。先占位不丢数据，等概念落地再实现——和人格按角色选择是同一件事，一起做。

**D9. 规则和人格的分界线：违反它是 bug 还是风格？** 模型违反了这条，你第一反应是"出 bug 了"还是"风格不对"？bug → 规则（必须强制）；风格 → 人格（可以商量）。
> 为什么：防止"回复必须简洁"这种可商量的事被写进硬规则，也防止"禁止数据外泄"这种硬约束被当成语气问题。

---

## 4. 人格（3 条）

**D10. 多个人格合并成一个人。** 仓库里有多个人格文件？M0 阶段全部按顺序拼成一个人格。
> 为什么：按角色选人格是 M5 的事（和 D8 一起）。现在先合并，冲突靠评审把关，lint 会提示"将要合并"。

**D11. 语言是给机器看的，语气是给模型看的。** `language`（中文 / 英文）是结构化字段，机器能消费（映射引擎的语言设置）；`tone`（专业、简洁）只是提示词文本的一部分。
> 为什么：语言影响配置（机器管），语气影响表达（模型管），各归其位。

**D12. 人格统一按"会话级"注入。** 编译后进 Codex 的 developer instructions 和 DSH 的 persona 段——都是"这次会话的人格"。
> 为什么：Codex 还有个"模型级人格"（friendly / pragmatic 预设），那是模型厂商的东西，租户不该去覆盖引擎内置模板。我们只管会话级。

## 5. 运行参数（4 条）

**D13. 沙箱和审批用一套统一词汇。** 只读 / 工作区可写 / 完全放开；从不问 / 每次问 / 信任名单不问。
> 为什么：与 Codex 同名（少一层翻译），DSH 的旋钮可映射，而且"只读默认"正是产品定位。

**D14. 权限没有例外通道。** runtime.yaml 里不让你手写权限段，写了 CI 直接报错。
> 为什么：一旦允许"例外"，就回到双写漂移。临时放行？写一条临时规则走 PR——可审计、可回滚，比例外口子干净。
> 人话：**一切权限皆规则，没有后门。**

**D15. 记忆服务先占个位。** `memory: { provider: ... }` 只声明"用哪种记忆"，细节（地址、范围）等 M1 调研定。
> 为什么：Codex 有原生记忆（MEMORY.md），DSH 走 MCP 记忆服务——两边差异还没调研完（附录 A.7.3），现在定字段必然猜错。占位不猜。

**D21. 配置分三层，钥匙不进仓库。** 引导配置（本地选引擎/模型/填凭证）→ 文档配置（进 Git 的 runtime.yaml：engine/model/参数）→ 秘密配置（token/凭证，env 注入，**绝不进 Git**）。
> 为什么：把模型 token、git 凭证写进 runtime.yaml = 把钥匙挂在门上——PR 评审可见、历史永久留存，治理模型毁于一旦（D14 同款：没有例外）。
> 人话：**配置可以进仓库，钥匙永远不进。**

## 6. 文档装配（1 条）

**D20. 跨家族的 order 用同一把尺子。** rules 与 prompts 的 `order` 是**全局统一编号空间**——一个文档库只有一套顺序编号，跨家族数值冲突（如两条规则和一个人格都是 20）由 lint 直接报错，不留模糊地带。
> 为什么：编译到引擎视图（AGENTS.md / system-prompt）时，所有文档要排成一条线。两套编号空间意味着合并时要么猜、要么另定规则。一把尺子，冲突即报错，顺序永远是确定的。
> 人话：**全仓库按一个序号排队，重号就报错。**

## 7. 租户模型与数据边界（4 条）

**D16. 数据分三层，绝不混。** Git 仓库 = 应用的源代码（共享）；运行时状态库 = 用户的私人状态（对话 / 记忆 / 偏好，按会话隔离）；业务数据 = 留在既有系统里（经工具访问，用户级授权）。
> 为什么：把用户数据塞进 Git 仓库 = 仓库爆炸 + 源代码和运行时数据混洗，Git 治理直接失效。
> 人话：**仓库装大脑，状态库存私人，业务数据留原处。**

**D17. 技能是分层叠加的。** 平台内置包 → 行业模板包（M4）→ 租户自有，同名就近覆盖；多产品 = 多租户仓库。
> 为什么：一个产品一套技能是默认，但"模板 + 定制"是真实需求——DSH 的分层注册表就是现成模型（最近者胜）。

**D18. 工具四态：用、选、指、装。** 使用天然支持（引擎都是 MCP 客户端）；选择受边界约束（已注册 ∩ 权限允许）；指定靠 skill 引用（注册仍在 runtime.yaml）；**安装必须走 PR**（AI 提议 → 评审 → 生效），运行时直装不做。
> 为什么：新工具 = 新权限面。自动安装听起来爽，但等于让 AI 自己给自己开权限——必须过 PR（D14 的延伸）。

**D19. 仓库不只装大脑，还装世界模型。** 仓库 = 行为文档（rules/skills/prompts/configs）+ 世界知识文档（network.md 这类 harness 梳理生成的认知）。判据：**值得人评审、会被人改、版本重要 → 进 Git；即时状态、高频、不值得评审 → 留 DB**。toB：租户仓库 `knowledge/`；toC：产品仓库 `users/<uid>/`（用户量级过大时降级到存储层）。知识文档先自由格式，schema 等 M1 验证再定。
> 为什么：网络维护 AI 的 network.md 是"这个世界长什么样"——harness 生成、人评审、版本化，和代码一个待遇；MIS 流水是即时状态，进 DB。
> 人话：**大脑进仓库，世界模型也进仓库，流水数据留 DB。**

## 8. 贯穿所有决策的三条原则

1. **单一事实源**：同一件事只写一份。工具注册（一份 runtime.yaml）、权限（由规则生成）、人格（合并成一份）。
2. **信息不丢**：引擎做不到的，藏在 metadata 带着走（D2、D4、D8）。
3. **机器可校验**：所有低级错误（引用不存在的工具、写错颜色、手写权限）由 CI 兜底，不靠记性。

---

## 9. 三个常用判据（写文档时问自己）

1. 违反它是 **bug 还是风格偏好**？→ 规则 or 人格（D9）
2. 这是 **注册还是引用**？→ runtime.yaml or skill 依赖（D3）
3. 引擎支持吗？不支持就 **不给能力但带信息**（D2、D4、D8）
