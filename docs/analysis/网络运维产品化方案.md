# 从探针脚本到网络运维产品：落地方案

> 面向"内网拓扑 + 网络质量 + 配置台账 + 持续运维"的产品化设计。
> 本文基于 `C:\project\deepseek-harness`（DSH）**已验证**的真实机制：profile 分层、存储域、凭据 seam、headless 一次性任务、API Gateway、Webhook。

---

## 0. 一句话结论

**DSH 做"决策面"，探针做"数据面"，两者必须解耦。**

- **数据面**（采集）：确定性、可版本化、可离线、可单测的原生探针进程。产出**结构化事实**，不产出自然语言。
- **决策面**（DSH）：把事实翻译成根因假设、影响面判断、处置建议、报告与工单。
- **闭环**：事实 → 存储 → 规则告警 → LLM 归因 → 人工审批 → 适配器执行 → 复测验证。

本次会话已经证明"单点脚本 + LLM 能在 30 分钟内定位根因"，但**证明了能力，不等于有产品**。缺口在下一节。

## 1. 本次会话做对了什么、缺什么

| 能力 | 本次实现 | 产品化要求 | 差距等级 |
|---|---|---|---|
| 拓扑发现 | Ping 扫段 + ARP + 端口指纹 + SSDP/ONVIF/mDNS | 以 MAC 为主键的**持久图**，多源证据（LLDP/SNMP/AP 关联表/DHCP 租约）收敛 | 🔴 大 |
| 设备识别 | MAC OUI 在线 API + TCP 9999 私有协议 + 证书/ISAPI 指纹 | **离线 OUI 库 + 指纹库版本化**，识别规则可热更新、可回归测试 | 🟠 中 |
| 无线质量 | `netsh wlan` 扫描 + BSS Load 聚合 | 需要 **AP 侧关联表**（客户端在哪个 AP/频段/RSSI/重传），单点扫描只能看"邻居" | 🔴 大 |
| 有线质量 | 延迟/抖动/丢包 + `netstat -e` | SNMP 读交换机端口（CRC/丢弃/双工/STP 变更）+ 探针间 TWAMP | 🔴 大 |
| 配置收集 | 无（只读了无凭据的公开面） | **凭据仓库 + 只读适配器**（SNMP/SSH/厂商 API） | 🔴 大 |
| 历史与趋势 | 无，全是"此刻快照" | 时序存储 + 基线 + 漂移检测 | 🔴 大 |
| 执行/下发 | 人工照着建议点 Web UI | 审批 → 适配器下发 → 复测 → 审计 | 🔴 大 |
| 交付形态 | 我临时写的 8 个 `.ps1` + 动态 Cordis 插件 | **动态插件随进程消失，永远不是产品**：必须是 package + composition row | 🔴 大 |

**一句话**：缺的不是 LLM，是**数据面、历史数据、凭据、执行闭环**这四块地基。

## 2. DSH 怎么放到后台用

### 2.1 先理解 Profile（这是后台化的载体）

`dsh` 启动的是 **profile**。已验证的真实布局：

```
$DSH_HOME/profiles/<name>/          # Windows: C:\Users\<user>\.dsh\profiles\<name>\
├── package.json      # 声明 dsh.profile.bundles 顺序 + dsh.profile.patchReload
├── cordis.yml        # 空根入口列表（dsh 生成，不要手改）
├── cordis.patch.yml  # ← 该 profile 自己的层，产品/客户改这里
└── node_modules/     # 该 profile 的插件依赖（由 dsh plugin 管理）
```

**层序**（后写的覆盖前面的，已从 `profile-boot.ts` 确认）：

```
bundle 层（package.json 的 dsh.profile.bundles 顺序）
  → profile 自己的 cordis.patch.yml
    → $DSH_HOME/cordis.patch.yml（全机器级用户层）
      → --patch <file>（命令行叠加，可重复）
        → telemetry 开关
```

`dsh --profile <name> --dump-config` 会打印合成后的完整树并标注每层来源 —— **这是产品自检的第一诊断工具**。

### 2.2 三种后台形态（按场景选，可组合）

| 形态 | 命令 | 生命周期 | 适合 |
|---|---|---|---|
| **A 常驻服务** | `dsh --profile netops --patch <overlay>` | 常驻进程 | UI、交互会话、告警处理、API 服务 |
| **B 一次性任务** | `dsh --profile headless --patch <overlay> "<task>"` | 秒~分钟退出 | OS 计划任务驱动的周期采集/巡检 |
| **C 嵌入式** | `dsh-sdk-app`（stdio JSON-RPC）/ `acp-app` | 随宿主进程 | 集成进客户既有的网管/工单平台 |

**推荐组合：A 常驻 + B 兜底。**

- 常驻进程负责**交互与 UI**（出问题时人要能马上追问）。
- 周期采集用 **B + 操作系统调度器**，因为：进程崩了不影响采集连续性；每轮都是干净上下文，不会被长会话的 token 拖累；出问题能单独重跑某一轮（可复现）。

### 2.3 关键判断：**不要用 `dsh-schedule` 做产品级调度**

`@deepseek-ai/dsh-schedule` 是"会话本地持久提醒"（`schedule_create/list/delete`），它的边界很硬：

- 交付**只发生在该会话内**，冷会话不触发、无邮件/短信/推送；
- 最小间隔 **5 分钟**，只支持固定间隔，**不支持 cron 日历规则**；
- 需要该会话的根 agent 处于 live 状态。

它适合"我在这个会话里让它每 20 分钟看一眼"，**不适合**产品的采集调度。产品调度放 OS（systemd timer / Windows 计划任务）或消息队列。

### 2.4 后台化实操

**Windows（计划任务，开机自启、隐藏窗口）**

```powershell
# 常驻服务
schtasks /Create /TN "DSH-NetOps-Service" /SC ONSTART /RU SYSTEM /RL HIGHEST ^
  /TR "cmd /c cd /d C:\netops && dsh --profile netops --patch C:\netops\overlay\svc.yml >> C:\netops\logs\svc.log 2>&1"

# 每 5 分钟一轮采集（一次性任务，跑完即退）
schtasks /Create /TN "DSH-NetOps-Probe" /SC MINUTE /MO 5 /RU SYSTEM /RL HIGHEST ^
  /TR "cmd /c cd /d C:\netops && dsh --profile headless --patch C:\netops\overlay\probe.yml \"执行一轮网络采集并在有异常时生成报告\" >> C:\netops\logs\probe.log 2>&1"
```

> 需要以服务方式托管（自动重启、无窗口）时用 [NSSM](https://nssm.cc/)，比 `schtasks` 更可控；或用 `apps\desktop` 打包成常驻托盘程序。

**Linux（systemd）**

```ini
# /etc/systemd/system/dsh-netops.service
[Unit]
Description=DSH NetOps Service
After=network-online.target

[Service]
Type=simple
User=netops
WorkingDirectory=/opt/netops
ExecStart=/usr/local/bin/dsh --profile netops --patch /opt/netops/overlay/svc.yml
Restart=always
RestartSec=5
StandardOutput=append:/var/log/netops/svc.log
StandardError=append:/var/log/netops/svc.log

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/dsh-netops-probe.service + .timer（每 5 分钟）
[Timer]
OnBootSec=2min
OnUnitActiveSec=5min
```

**工程要点**：探针进程必须**幂等、可重入、可重跑**；每轮产出带 `run_id` 的事实文件，失败只影响本轮；日志按天轮转。DSH 的 `packages/jobs` 提供后台作业注册表，长任务（如整段 iperf3 或批量 RTSP 拉流）走它而不是阻塞会话。

### 2.5 触发方式不止定时

- `@deepseek-ai/dsh-webhook`：外部告警/工单系统 POST 进来 → 直接创建一个 Session 做归因分析（fire-and-forget）。
- **事件驱动**比轮询更适合"网络抖动"这类瞬时事件：探针发现异常 → 落库 → webhook 触发 DSH 分析 → 产出报告 + 通知。

## 3. 产品架构

```
┌─────────────────────────── 呈现层 ───────────────────────────┐
│ Web UI: 拓扑图 / 质量热力 / 设备台账 / 配置差分 / 告警 / 报告   │
│ 开放 API（供客户网管/工单系统集成）                            │
└───────────────────────────────┬──────────────────────────────┘
                                │ HTTP /api/<ns>/<method>（Typert API Gateway）
┌───────────────────────────────┴──────────────────────────────┐
│                        决策面（DSH Profile: netops）          │
│  · 规则引擎：阈值 / 趋势 / 基线偏离 / 突变                     │
│  · LLM Agent：根因假设、影响面、处置建议、报告、工单草稿        │
│  · 模型分级：日常汇总用便宜模型，根因分析用强模型（workflow 支持按阶段指定 provider/model）│
│  · 审批：permission-presets + user-approval（写操作必须人工确认）│
└───────────────────────────────┬──────────────────────────────┘
                                │ 读事实 / 写建议
┌───────────────────────────────┴──────────────────────────────┐
│                      存储层（$DSH_HOME/storages 或外部 DB）    │
│  storage-domain（schema 校验 + 事件发射的 KV 域）              │
│  后端：storage-sqlite / storage-json（可替换为 Postgres）      │
│  域：topology / samples(时序) / inventory(配置快照) / findings │
└───────────────────────────────┬──────────────────────────────┘
                                │ 结构化事实（JSON）
┌───────────────────────────────┴──────────────────────────────┐
│                   采集层（确定性探针，非 LLM）                 │
│  本机探针 + 分布探针（每个网段/每台 AP 挂一个）                │
│  ├ 主动：ICMP/TCP/UDP、traceroute、iperf3、RTSP 拉流取样       │
│  ├ 被动：ARP/DHCP/SSDP/ONVIF/mDNS 嗅探、sFlow/NetFlow（可选）  │
│  └ 适配器：SNMP v2c/v3、SSH 只读 CLI、厂商 API                  │
│            （xFi/Omada/Tapo/UniFi/海康 ISAPI/大华/ONVIF）      │
└──────────────────────────────────────────────────────────────┘
```

### 事实层 / 推理层边界（这条线决定产品能不能挣钱）

| | 事实层（探针） | 推理层（DSH/LLM） |
|---|---|---|
| 输出 | 定长 JSON：`{metric, value, unit, ts, src}` | 自然语言 + 结构化 Finding/建议 |
| 可重复性 | 必须 100% 可重复 | 允许不确定性，但必须给证据链 |
| 成本 | 近乎为零（本地计算） | 有 token 成本，必须**按事件触发**而非全量常跑 |
| 失败处理 | 重试 + 部分成功上报 | 降级为"证据不足"而不是编造 |
| 测试 | 单测 + 回放历史数据 | 评测集 + 人工抽检 |

**绝对不要把原始指标喂给 LLM 让它"看"**。让探针算好"ch11 利用率 45%、同信道 11 个 BSS、摄像头 .177 抖动 31ms 丢包 5%"，LLM 只负责说"这就是卡顿根因，建议把 H3C 的 2.4G 挪到 ch6"。

## 4. 数据模型（产品的地基）

以 **MAC 为主键**做设备身份 —— IP 会变、DHCP 会重分配，这是本次会话里 `10.0.0.229`（WLAN 残留）和 `10.0.0.236` 并存教给我们的。

```
Site(站点)
 └─ Segment(网段/VLAN/SSID)：cidr、vlan_id、ssid、band、security、gateway
     └─ Node(设备)：node_id(=规范化MAC)、vendor、model、firmware、type、
     │              role(camera/ap/nvr/switch/iot/client)、first_seen、last_seen、
     │              ip_history[]、hostname[]、credential_ref
     └─ Link(链路)：a_node、b_node、a_if、b_if、medium(wired/wifi)、
     │              band、channel、rssi、snr、negotiated_rate、duplex、evidence(LLDP|ARP|AP关联|DHCP)
     └─ Sample(采样)：node_id、metric、value、unit、ts、run_id      ← 时序，量最大
     └─ Finding(发现)：severity、category、evidence[]、affected_nodes[]、
     │                 first_seen、last_seen、status(open/acked/fixed)
     └─ Action(建议/变更)：finding_id、proposal、risk、requires_approval、
                            approved_by、executed_at、verify_result
     └─ ConfigSnapshot(配置快照)：node_id、ts、source(snmp/ssh/api)、
                                   normalized_json、hash、diff_vs_prev
```

**三条约束**：

1. `Sample` 必须能按 `node_id + metric + 时间窗` 聚合（降采样：原始 5 分钟 → 1 小时 → 1 天）。
2. `Finding` 必须有 `evidence[]` 指回 `Sample`/`Snapshot`，否则 LLM 的结论无法审计。
3. `ConfigSnapshot` 存**归一化 JSON + hash**，差分只算 hash 变化，避免全量比对。

## 5. 四大能力域的实现路径

### 5.1 拓扑探索

| 层 | 数据源 | 产出 |
|---|---|---|
| L2 真实拓扑 | **SNMP Bridge-MIB**（dot1dTpFdbTable/dot1dBasePortTable）、**LLDP-MIB**、交换机 MAC 表 | 设备→交换机端口的物理连接图 |
| L3 | 路由表、traceroute、ARP | 网段与网关关系 |
| 无线 | **AP 侧关联表**（SNMP dot11 或厂商 API） | 客户端→AP→频段→信道→RSSI |
| 名称/角色 | DHCP 租约（网关 API/RouterOS/OpenWrt）、mDNS、NetBIOS、ONVIF、厂商云 | 人类可读名字与设备角色 |

**教训（本次踩到的坑，产品必须内置）**：探针发广播/组播前**必须显式绑定出口接口**。这台机器的 `255.255.255.255` 被 VirtualBox Host-Only（metric 25）抢走、`224.0.0.0/4` 最低度量在 Wi-Fi Direct 上，导致默认套接字的 SSDP/ONVIF 探测 **0 响应**；显式绑定 `10.0.0.236` 后立刻收到 19 个响应。**产品第一步就该是"出口接口自检"**并给出修复建议 —— 这本身就是一条产品化的 Finding。

### 5.2 网络质量

**有线**（SNMP ifTable/ifXTable/EtherLike-MIB）：

- 错包：`ifInErrors`、`dot3StatsFCSErrors`（CRC）、`ifInDiscards`
- 物理：协商速率、双工（`dot3StatsDuplexStatus`）、`ifMauType`
- 拓扑稳定性：`dot1dStpTopChanges`（STP 抖动 = 环路/接错线）
- 质量：探针↔探针 ICMP/TWAMP 时延抖动、`iperf3` 定时吞吐

**无线**（AP API/SNMP + 探针扫描）：

- 空口：**信道利用率**、噪声底、同信道/邻信道 BSS 数、最大 BSS
- 客户端：RSSI/SNR、协商速率、**重传率**（`dot11FailedCount`/`dot11RetryCount`）、省电模式
- 关联：客户端数、频段分布、漫游事件
- **这是定位"摄像头卡顿"的关键**：本次只能靠"这台 Tapo 抖动 31ms、那台海康 4ms"来**推断**它在 Wi-Fi，产品必须能直接读出"该摄像头挂在 AP2 的 2.4G ch11，RSSI -67，重传 23%"。

**视频体验（对摄像头场景是杀手级指标）**：拉一路 RTSP 抽样 30 秒：

- 码率稳定性（方差）、关键帧间隔、丢帧/花屏计数
- 端到端"卡顿指数"：`f(丢包率, 抖动, 码率方差, 重传率)` → 0-100 分
- 输出"这路摄像头当前体验 72 分，瓶颈在 2.4G 空口"**而不是**让用户自己看画面猜

### 5.3 配置与账号收集

**凭据**用 DSH 现成的 seam（`packages/credentials` + `credentials-local`）：

- `cordis.yml` 和 settings 里**只放引用名**（POSIX 风格环境变量名），值归 provider；
- 本地 provider 分层：`env` / `file` / `project-env` / `user-env`，落盘在 `$DSH_HOME/.credentials.yaml`；
- **每次操作重新解析、绝不缓存** → 改密码后下一次请求即生效，**无需重启**；
- `describe(ref)` 只回"是否已配置/来自哪层/可否写"，**永不回值** → 这条读路径可以安全地走后端接口给 UI 用。

**适配器清单**（按优先级）：

| 目标 | 协议 | 只读能力 | 写能力 |
|---|---|---|---|
| 网关 | 厂商云 API（xFi）/ 本地 Web | 关联设备表、WAN 状态、信道 | ⚠ 多为云端托管，本地 Web 改不了信道 |
| AP/路由器 | SSH CLI、HTTP API、SNMP | SSID/信道/带宽/功率/关联表 | 改信道、改功率、重启射频 |
| 摄像头 | ONVIF（Profile S/T）、海康 ISAPI、大华、Tapo 本地 KLAP | 型号/固件/码流/编码参数 | 改码率/帧率/OSD |
| 交换机 | SNMP、SSH | 端口状态/MAC 表/错误计数 | 端口开关、VLAN |

**本次会话的两个硬约束，产品必须在需求阶段就承认**：

1. **Xfinity 网关的信道被 Comcast 云托管**，本地 Web UI 只读（`Channel Selection` 置灰）。产品在这种情况下能力上限就是"检测 + 建议到能在本地改的那个 AP（本次的 H3C）"，或者引导客户改 Bridge 模式。
2. **无管理员权限时无法做 DHCP 探测/原始套接字 SYN 扫描**。产品探针必须以管理员/root 安装（或接受能力降级并能如实上报"未采集"）。

### 5.4 运维闭环

```
采集 → 事实入库 → 规则命中 → Finding
  → LLM 归因（带证据链）→ 建议 Action
    → 人工审批（DSH permission-presets + user-approval）
      → 适配器执行 → 自动复测 → 结果回写 Action.verify_result
        → 未修复则升级/升级工单
```

配套能力：

- **基线**：设备/链路指标的正常区间，用 7-14 天数据自动生成，人工可覆盖；
- **漂移**：配置快照 hash 变化 → "谁在什么时候改了 SSID 密码"；
- **报告**：每日体检 + 事件复盘，LLM 生成但**必须引用 evidence**；
- **SLA**：关键摄像头可用率/体验分达标率。

## 6. 凭据、权限与安全（不能省的合规线）

1. **默认只读**。所有写操作必须显式开启，并逐次审批（`packages/guard`、`packages/sandbox`、permission-presets）。
2. **凭据永不落配置文件**，走 credentials seam；导出报告时脱敏。
3. **审计**：每次扫描/读配置/下发变更都留 `who/when/what/target/result`。
4. **扫描合规**：产品默认只扫自己管理的网段，且**首次使用需要客户确认授权范围**（本次会话中"扫别人的 Wi-Fi 列表"只是被动接收 beacon，属于正常；主动扫描/认证测试必须另开授权）。
5. **数据边界**：本地优先。云托管模式下只上传指标与拓扑，**不上传原始抓包**。

| **P0 最小闭环** | 1–2 周 | 把本次的 `.ps1` 变成正式探针包 + 事实入库 + 报告 | `dsh-netops-probe` 包；SQLite 落库；一键生成《网络体检报告》 |
| **P1 拓扑与多探针** | 3–6 周 | 多网段探针 + SNMP/AP 适配 + 拓扑图 UI | 拓扑图可交互；AP 关联表可见；出口接口自检内置 |
| **P2 质量与告警** | 6–12 周 | 无线质量指标 + 视频体验分 + 基线告警 + 配置快照/差分 + 凭据 | 卡顿定位到"哪个 AP/频段/客户端"；日报/周报；配置变更追踪 |
| **P3 闭环执行** | 12 周+ | 审批 → 下发 → 复测；多站点多租户；开放 API | 变更闭环审计；API 文档；客户网管集成 |

**P0 就能交付价值**：本次会话的全部诊断能力，产品化成"插上就能出报告"，这已经是可售卖的最小单元。

---

## 8. 交付形态

| 形态 | 说明 | 适合 |
|---|---|---|
| **一体机（推荐）** | Mini PC 预装 DSH + 探针，客户网络里插一根网线即可 | 家庭/小型办公室的多 AP + 摄像头场景 |
| 软件自部署 | 客户自己装 DSH profile + 探针 | 有 IT 能力的 SMB |
| 云 + 本地探针 | 本地探针只上报指标，云端做分析与多站点看板 | MSP/连锁门店 |

**为什么必须"在网内"**：本次诊断的每一条结论都依赖"探针在 LAN 内"——延迟抖动、BSS Load、ONVIF 发现、AP 关联。纯云端产品做不到这些。

---

## 9. 本周就能做的最小闭环

1. 建 profile 并挂上存储与凭据：`dsh plugin --profile netops add @deepseek-ai/dsh-storage-sqlite`（+ `dsh-credentials-local`）。
2. 把本次 8 个脚本重写成**一个探针包**，输出统一 JSON（见附录 schema），**先不做 LLM**。
3. 计划任务每 5 分钟跑一次 `dsh --profile headless --patch probe.yml "..."`，落 SQLite。
4. 加一条规则：`摄像头抖动 > 20ms 或丢包 > 2%` → 生成 Finding。
5. 只有 Finding 产生时，才调用 LLM 生成根因与建议（**按事件计费**，不是每次都跑）。
6. UI 先不做，用 DSH 自带的会话界面追问 + 导出 Markdown 报告。
