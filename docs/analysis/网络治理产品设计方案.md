# 网络治理产品设计与落地方案

> 面向 **有线 / 无线 / CCTV / 门禁 / IoT** 五域的统一治理平台。
> 形态：一台本地一体机（树莓派或笔记本），接入客户网络后自举运行。
> 技术栈：Docker + Web + PostgreSQL + TDengine + MQTT + DSH（Harness Chat）+ GitHub/GitOps。

---

## 0. 产品定位与三条铁律

**一句话定位**：插上网线就能"看懂、说清、管住"客户网络的一体机 —— 不只是监控，而是**设备可治理性**管理。

与通用 NMS 的区别：NMS 追"5 分钟粒度采全网 SNMP"；本产品追**"这台设备我能不能登录、能不能改、改了会不会坏、坏了怎么回滚"**。所以核心资产不是指标库，而是**设备台账 + 配置入口 + 操作手册（Runbook）+ 凭据**。

**三条铁律**（贯穿全部设计）：

1. **只读优先**：任何写操作都必须有客户显式授权范围 + 逐次审批 + 回滚点。
2. **凭据永不到达 LLM**：模型只能提"对 10.0.0.94 执行 X"，由凭据代理在内存中完成认证。模型上下文中永远没有密码。
3. **配置即代码**：客户网络的事实、期望态、策略、手册全部进 Git；变更走 PR，可审计、可回滚。

## 1. 五域能力矩阵

| 域 | 发现方式 | 质量指标 | 治理动作（风险分级） |
|---|---|---|---|
| **有线** | LLDP / Bridge-MIB / ARP / 交换机 MAC 表 | 端口 CRC·丢弃、双工/速率、STP 变更次数、时延抖动 | 端口开关、VLAN 划分（中） |
| **无线** | AP 侧关联表（SNMP/厂商 API）、专用监听网卡扫描 | 信道利用率、噪声底、同信道 BSS 数、客户端 RSSI/SNR/重传率、漫游事件 | 改信道/带宽/功率、踢客户端（中） |
| **CCTV** | ONVIF WS-Discovery、端口指纹、厂商 API | 码率稳定性、丢帧、**录像完整性**、NVR 硬盘健康、离线时长 | 改码率/帧率/OSD、重启、录像计划（中） |
| **门禁** | 厂商 HTTP/SDK、端口指纹 | 在线率、事件上报延迟、门磁状态、控制器时钟偏差 | 权限/时段（中）；**远程开门列为禁止自动化**（极高） |
| **IoT** | mDNS / SSDP / MQTT / Tuya 局域网 / Matter | 在线率、RSSI、回包延迟、固件版本 | 基本只读；重启（低）、固件升级（高） |

> 门禁的"远程开门"和防火墙的策略放行，**产品永久不提供自动执行**，只提供"点哪里"的引导。

### 关键架构决策：**DSH 的存储不做产品主库**

DSH 自带的 `storage-domain` 是 **schema 校验 + 事件发射的 KV 域**，适合会话与投影，不适合"按设备+指标+时间窗聚合"的时序查询和关系查询。所以：

- **产品主数据 → PostgreSQL + TDengine**
- **DSH 自己的会话/投影 → 保留其 native 存储**（`$DSH_HOME/storages`）

两边不互相迁就，通过 API Gateway 通信。这是让产品能长大的前提。

### 关键架构决策：**Harness 选型与服务化边界**

**架构前提（已修正）**：Web 前端**独立建设**，直接从数据层（PG / TD / MQTT）渲染，只把**部分任务**委派给 Harness。于是 Harness 不再是 UI 载体，而是**任务推理后端** —— 选型判据随之改变：**不看它有没有 UI 能力，只看它能不能被"程序化驱动 + 结果结构化 + 会话可落库"**。

```
独立 Web ──直接读──> PostgreSQL / TDengine / MQTT      ← 页面渲染走这里
   │
   └──委派任务──> AgentBackend（我们自己定义的接口）
                    └─ 适配器 ──> DSH / Pi / Claude SDK / Codex
                         · 输入：我们组装的结构化事实包（脱敏、无凭据、有界）
                         · 输出：JSON Schema 约束的结论 / 建议 / 变更草案
                         · 不持凭据、不执行写操作、不直连设备
```

**决定性设计规则：Harness 只读不写 —— 审批需求由架构满足，而不是靠 harness 的权限系统。**

写操作（改信道、改码率）**不作为 harness 的工具存在**。harness 只输出结构化的"变更草案"，由我们的后端走审批、worker 执行。于是：

- 铁律 #1（写操作必须审批）由**架构**保证，不依赖任何 harness 的权限模型；
- 不需要长审批阻塞 agent 进程；
- **Harness 变成可替换的商品**，选型风险大幅下降。

**三家 harness 的服务化 API 现状**（2026-09 核实的官方文档）：

| 能力 | Claude Agent SDK | Codex（SDK + app-server） | Pi（RPC + AgentSession） |
|---|---|---|---|
| 驱动方式 | TS/Py 库，`query()` spawn `claude` CLI over stdio；另有托管的 **Managed Agents REST API** | `@openai/codex-sdk`（spawn CLI，JSONL）+ **app-server JSON-RPC**（`thread/*`、`turn/start`） | `pi --mode rpc` JSONL 协议；Node 可**进程内**用 `AgentSession` |
| 会话落库 | ✅ `SessionStore` 适配器（S3/Redis/**Postgres**）+ `resume` by id | ✅ threads 持久化 + `resumeThread` | ✅ session 文件 + `get_entries since` 持久游标 |
| 结构化输出 | ✅ structured outputs | ✅ `outputSchema`（JSON Schema / Zod） | ✅ 工具 + extension |
| 工具扩展 | ✅ 自定义工具 + MCP | ✅ MCP | ✅ TypeScript extension |
| 审批回调 | ✅ `canUseTool`（allow/deny/改参）+ `AskUserQuestion`；`PreToolUse` hook 可 `defer`，进程退出后从持久会话恢复 | ⚠️ 权限配置 + app-server（逐次审批回调需自建） | ✅ extension UI 协议（select / confirm） |
| 凭据隔离 | ✅ 官方建议：工具凭据**不进 agent 环境**，由 egress proxy 在请求离开容器后注入 | ⚠️ 自建 | ⚠️ 自建 |
| 多租户隔离 | ✅ 官方文档：`settingSources: []`、独立 `CLAUDE_CONFIG_DIR`/`cwd`、per-tenant egress | ⚠️ 自建 | ⚠️ 自建 |
| 可观测 | ✅ OpenTelemetry（traces / metrics / logs） | ⚠️ | ⚠️ |
| 每会话资源 | **官方给出 1 GiB / 1 CPU / 5 GiB disk per agent 起**，随会话长度增长 | 同类子进程模型 | 进程内 `AgentSession` 最省 |
| 模型 | Anthropic（+ Bedrock / GCP） | OpenAI | **15+ provider，含 Ollama** |
| 许可 | 商用 SDK | 商用 | **MIT** |

来源：[Claude Agent SDK hosting](https://code.claude.com/docs/en/agent-sdk/hosting) · [approvals](https://code.claude.com/docs/en/agent-sdk/user-input) · [Codex TypeScript SDK](https://github.com/openai/codex/blob/main/sdk/typescript/README.md) · [Codex app-server](https://github.com/openai/codex/tree/main/codex-rs/app-server) · [Pi RPC](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md) · [pi.dev](https://pi.dev/)

**选型结论：先定义 `AgentBackend` 接口，harness 按客户条件选适配器，不作为产品本身。**

| 客户条件 | 选的适配器 |
|---|---|
| 客户指定 Anthropic / 要最强的审批与多租户官方支持 | **Claude Agent SDK** |
| 客户指定 OpenAI | **Codex**（app-server / SDK） |
| **离线 / 自选模型 / 最低资源占用**（Pi 一体机的常见约束） | **Pi**（MIT + Ollama + 进程内 `AgentSession`） |
| 需要深度定制产品行为、并接受自己承担运维 | **DSH**（本仓库；profile + credentials seam） |

> **DSH 的定位随架构修正而改变**：它的优势不再是"现成的 UI 与审批"（因为 Web 与审批都在我们这边），而是**"完全可控、可改源码、无供应商锁定"**；代价是多租户、可观测、托管这些要自己扛。本项目当前正跑在 DSH 上，短期以它落地成本最低，但**接口要按可替换来设计**。
>
> **本机核实结果（纠正上一版说法）**：DSH **不是**与 Pi 无关。`@deepseek-ai/dsh-llm-pi-ai v0.1.5-rc.2` 已安装在 `~/.dsh/profiles/node_modules`，依赖 `@earendil-works/pi-ai ^0.85.1`，并在 `@deepseek-ai/dsh-base` 的 composition 里**以 dormant 方式挂载**：默认零路由、模型选择器里不出现额外模型，直到 `$DSH_HOME/settings.yaml` 里给出 `llm-pi-ai:` 段才激活（该文件**热加载**，Web 的 Models 页写的就是它）。
>
> **含义：模型层不需要二选一。** 运行时留在 DSH 拿它的工具/作业/审批治理，模型广度（15+ provider，含 Ollama 离线）通过 `llm-pi-ai` 适配器获得。
>
> 另：**DSH 与 Pi 同为 MIT 许可**（DSH 根包 `license: MIT`，Copyright 2026 DeepSeek），**许可证不是差异点**。

### 工具编排轴：DSH vs Pi（本产品的核心任务）

产品的核心任务就是"调各种网络工具、选择工具、必要时造工具"，那么逐项对比：

| 维度 | DSH | Pi |
|---|---|---|
| 造工具入口 | `cordis_define`（写插件体）→ `cordis_run` **立即激活** | 写 TS extension 文件 → `/reload` |
| 生效延迟 | 下一步即可调用 | reload 之后 |
| **版本化** | ✅ **不可变 Package + 版本指针**（`currentPackageId` / `nextPackageId`） | ❌ 自己用 git 管 |
| **授权** | ✅ **按版本授权**（单勾=仅本次；双勾=该插件后续版本） | ❌ 无 |
| 停止 / 回滚 | ✅ `cordis_stop`（保留定义与版本指针） | 手动 |
| 持久化 | 需落成 package + composition row（有正式路径） | ✅ **文件即持久** |
| 分发 | profile / npm | npm / git package |
| Host + Client 双面工具 | ✅ 两侧都能造 | 仅 TS extension |
| **工具执行的治理**（沙箱 / 审批 / 权限） | ✅ host 一等公民（`sandbox`/`guard`/`permission-presets`） | ⚠️ 用 extension 自建（有示例） |
| **长任务** | ✅ `jobs` 注册表（后台、取消、完成通知） | ⚠️ 官方"无 background bash"，建议 tmux |
| **并行分域** | ✅ subagent 注册表 + `tool-workflow` | ⚠️ 自建 |
| MCP 生态 | ✅ `packages/mcp` | ❌ 官方"No MCP" |
| 超大工具输出 | ✅ `packages/spill`（截断 + 溢出到文件并回报路径） | ⚠️ bash 截断 + `fullOutputPath` |
| 许可 | MIT | MIT |

**判读**：**"选择工具"两家都行**，取决于工具描述质量与模型能力，不是选型差异。**"创造工具"才是分水岭**，但分水岭不在"能不能造"，而在**造出来的东西归谁管**——Pi 摩擦最低且天然持久，DSH 则有版本、授权、回滚语义。对一个会在**客户生产网络**上执行代码的产品，后者才是可交付的。

### 关键产品判断：**造工具不该发生在生产运行时**

让模型在客户生产网络上**现场造工具并以 root 执行**，是不可审计、不可回归、出事无法解释的设计。正确做法是**两级工具工厂**：

| 阶段 | 人在环 | 做什么 | 产物 |
|---|---|---|---|
| **接入期**（offline） | ✅ 人审 | 模型辅助生成适配器草案 → 实验室真机验证 → 回放样本 + 单测 | 进适配器库（Git、版本化、`verified` 标记） |
| **运行期**（online） | ❌ 无人 | 模型只**选择**已审核工具 + **组合**它们（编排脚本，不写特权操作） | 结论 / 建议 / 变更草案 |

运行期的"组合"正是 DSH 的 **PTC（programmatic tool calling）+ `code-runtime` worker** 与 `tool-workflow` 的用武之地：让模型写一段代码**一次调用多个只读工具**，而不是 N 轮往返——省 token、可回放、可测。

### 给 harness 的工具应当是"领域能力"，不是裸工具

不要给模型 `snmpwalk`，给它复合能力：

```
probe_snapshot(segment_id)          → 有界 JSON
device_config(device_id, section)   → 归一化配置 + 差分
cctv_health(camera_id)              → 码率稳定性 / 丢帧 / 体验分
wifi_environment(ap_id)             → 信道利用率 / 噪声 / 关联表
```

每个复合工具内部执行几十个原始操作，对外只回**有界蒸馏结果**。好处：上下文不炸、**每个复合工具天然是一个授权单元**、换 harness 不动工具层、模型仍有充分的选择空间。

### 两个必须现在就认的风险

1. **`dsh-llm-pi-ai` 是"design-verification twin"**：官方描述明确它是为**验证 LLM seam 设计**而做的孪生实现，**不是主打的多 provider 生产路径**。要拿它做生产，先验证 provider 覆盖、Ollama 的工具调用能力、错误与重试行为。**这是工作量，不要当成既成事实排期。**
2. **DSH 当前版本 `0.1.5-rc.2`（release candidate）**：把 rc 作为商业产品地基，必须现在定升级策略（锁版本 + 定期评估 + 变更评审 + 回归测试集）。

**服务化的关键边界（这条决定成败）**：

```
控制面（harness 负责）              数据面（harness 不参与）
· 会话 / 上下文 / 工具编排           · 采集：探针直接写 MQTT / DB
· 根因推理 / 报告叙述                · 执行：worker 直接调适配器
· 审批流 / 凭据代理                  · 时序写入：探针 → TDengine
· Runbook 检索 / 对话引导            · 事件总线：MQTT
```

**绝对不要把数据面塞进 agent turn**。若每个采样点都过一遍 agent loop，成本与延迟都会爆，而且 chat 会被长任务阻塞。

正确姿势：chat 说"做一次全网扫描" → harness 用 `jobs` 建作业并**立即返回** → 探针/worker 执行 → 结果进 MQTT/DB → harness 收到通知再叙述。**长任务永远异步**。

**"一定通过 harness 走外网"的正确含义**：所有模型调用只从 harness 的 LLM 适配器出去，它因此成为唯一出口 —— 好处是**单一审计点**（哪些数据离开了客户网络）、**单一成本点**（token 核算/限流/配额）、**单一密钥点**（凭据轮换一处生效）。代价是：

- harness 挂了 → 所有 AI 能力挂（但**采集不挂**，这正是控制面/数据面分离的价值）；
- 客户出口若封锁模型 API 域名 → 需要代理/白名单方案，**售前必须确认**（可参考官方建议的 egress proxy 模式：代理做域名白名单、注入凭据、记录请求）；
- **三家都是"一个会话 = 一个子进程"模型**（Claude SDK 与 Codex 显式如此，Pi 的 RPC 模式亦为独立进程；仅 Pi 的进程内 `AgentSession` 例外）→ **并发数直接等于受限资源**，必须用队列串行化，而不是让十来个会话同时开。

## 3. 探针设计（需求 2）

### 3.1 部署形态

```yaml
# 关键：探针必须拿到真实网卡与原始套接字
network_mode: host
cap_add: [NET_RAW, NET_ADMIN, NET_BIND_SERVICE]
# 无线监听（可选）：挂载无线网卡
devices: ["/dev/bus/usb"]
```

**必须显式绑定出口接口**——这是本次会话踩到的真实坑：机器上 VirtualBox Host-Only（metric 25）抢走了 `255.255.255.255` 广播路由、Wi-Fi Direct 抢走 `224.0.0.0/4` 组播，导致默认套接字的 SSDP/ONVIF 探测**静默 0 响应**；显式绑定 `10.0.0.236` 后立刻收到 19 个响应。探针第一件事就是跑**能力自检**：

| 自检项 | 判定 | 失败后果 |
|---|---|---|
| 出口接口 | `Find-NetRoute 255.255.255.255` / `ip route get 224.0.0.0` 是否等于目标网卡 | 所有广播/组播发现失效 |
| 权限 | 能否发原始套接字、能否 ARP 扫描 | 只能做 TCP 扫描，邻居发现缺失 |
| 无线能力 | 是否有可用的 wlan 接口 / monitor 模式网卡 | 拿不到信道利用率与噪声 |
| 网关托管状态 | 本地 Web 是否只读（如 Comcast xFi 云托管） | 无法改信道，必须能力降级并如实上报 |
| 冗余网卡 | 是否存在多出口导致策略路由冲突 | 探测结果不可信 |

### 3.2 工具集成矩阵

| 类别 | 工具 | 产出 | 备注 |
|---|---|---|---|
| 二层发现 | `arp-scan`、`fping`、`nmap -sn` | 活动主机 + MAC | 比 ICMP 单发快 10 倍 |
| 服务指纹 | `nmap -sV`、自研 banner/证书指纹 | 端口·服务·型号 | 已有 OUI 库 + 指纹库版本化 |
| 拓扑 | LLDP-MIB、Bridge-MIB、`traceroute` | 端口↔端口真实连接 | ARP 只能给"同网段清单" |
| 设备配置 | `snmpwalk/get`(v2c/v3)、SSH 只读命令集、厂商 API | 配置快照 | 只读命令白名单，禁止 `configure` |
| 无线 | `iw`/`netsh` 扫描、专用监听网卡 | 信道利用率·噪声·邻居 BSS | **需外接支持 monitor mode 的网卡** |
| 性能 | `iperf3`、TWAMP、ICMP 抖动采样 | 吞吐·抖动·丢包 | 探针↔探针才是端到端真相 |
| 视频 | RTSP 抽样、ONVIF Media/PTZ、海康 ISAPI | 码率方差·丢帧·卡顿指数 | 对 CCTV 场景是杀手级指标 |
| IoT | mDNS/SSDP 嗅探、MQTT 订阅、Tuya/Matter | 设备清单与在线率 | Zigbee/Z-Wave 需网关 API |

> **许可证提醒**：`nmap`(GPL)、`arp-scan`(GPL) 在**一体机内自用不分发**通常无碍；若要把工具打包进对外销售的镜像，需逐个核对许可证，或改用自研实现。这条必须在立项时决定。

### 3.3 统一事实 schema（探针唯一对外契约）

```json

  "run_id": "2026-09-10T11:02:00Z-home-01",
  "probe": { "node_id": "30:43:d7:ed:61:7a", "iface": "eth0", "ip": "10.0.0.236", "privilege": "root" },
  "facts": [
    { "kind": "host",    "node_id": "e0:d3:62:b9:b9:87", "ip": "10.0.0.177",
      "vendor": "TP-Link", "model": "Tapo", "role": "camera", "confidence": 0.85,
      "evidence": ["arp","onvif"] },
    { "kind": "link",    "a": "30:43:d7:ed:61:7a", "b": "e0:d3:62:b9:b9:87",
      "medium": "wifi", "band": "2.4GHz", "channel": 11, "confidence": 0.6 },
    { "kind": "metric",  "node_id": "e0:d3:62:b9:b9:87", "metric": "icmp.rtt.jitter",
      "value": 31.6, "unit": "ms", "window_s": 60 },
    { "kind": "service", "node_id": "e0:d3:62:b9:b9:87", "port": 554, "proto": "tcp",
```

**`confidence` 是必需的**：探针只给"候选事实 + 置信度"，人工在 UI 上确认/修正后写回，并**沉淀进指纹库**（下次同类设备直接高置信）。

### 3.4 人工调整闭环（需求 2 的"人工进行调整"）

```

```

Chat 是这条闭环的加速器："把 10.0.0.204 标成 AP 不是路由器" → 直接落库并生成 PR。

## 4. 拓扑、治理入口与操作手册（需求 3）

### 4.1 设备可治理性四级模型（本产品的核心度量）

| 级别 | 名称 | 判定 | 产品能做什么 |
|---|---|---|---|
| **L0** | 在网 | 有 ARP/响应 | 只能说"它存在" |
| **L1** | 识别 | 命中厂商/型号/固件 | 给出身份、风险提示、默认端口 |
| **L2** | **可读** | 凭据可用，能采集配置 | 配置快照、差分、漂移告警 |
| **L3** | **可写** | 授权 + 适配器支持 | 受控变更、自动回滚 |

**产品首页最重要的数字不是"发现 29 台设备"，而是"29 台中 6 台 L2、2 台 L3、21 台还在 L0/L1"**——它直接告诉客户"你的网络有多少是黑的"。

### 4.2 设备卡片（每台设备一个可治理入口）

```
身份：厂商/型号/固件/序列号/首次发现时间
位置：楼层/房间/机柜/U位（或平面图坐标）
链路：上联设备/端口/介质/协商速率/当前带宽
服务：开放端口 + 服务指纹 + 暴露风险
凭据：credential_ref（引用名，无明文）
配置：查看入口（Web/CLI/App）、最近快照、与期望态差异
手册：命中的 Runbook（登录方式/常用任务/风险操作/回滚）
操作：只读采集 / 申请变更 / 生成 PR / 开 Chat
```

### 4.3 Runbook 知识库——**这是产品最值钱的资产**

**立场：Runbook 是策展资产，不是 LLM 生成物。** 让模型凭空写"如何进入 H3C 后台改信道"，在生产环境是危险的。设计：

| 字段 | 说明 |
|---|---|
| 匹配 | 厂商 + 型号正则 + 固件范围 + 开放端口特征 |
| 入口 | Web URL / CLI / App / 云平台 |
| 认证 | 认证方式（Digest/Basic/表单/私钥）、默认凭据警告、锁定策略 |
| 常用任务 | 改信道、改码率、加用户、看录像、导出配置 —— 每项含**精确步骤 + 截图/路径** |
| 风险操作 | 恢复出厂、固件升级、改 WAN、关防火墙 —— 标注影响与前置检查 |
| 回滚 | 备份命令/导出路径/恢复步骤 |
| 来源 | 官方文档链接 + 验证人 + 验证时间 + 适用固件版本 |
| 状态 | `draft` / `verified` / `deprecated` |

**生产流程**：领域专家撰写 → 在实验室真机验证 → 标记 `verified` → 入库版本化。
**LLM 的角色**：检索、按客户环境**裁剪**已验证的步骤、生成对话式引导，**不允许发明新步骤**。若某设备无 Runbook → 明确输出"暂无已验证手册，请提供型号或联系支持"，绝不编造。

### 4.4 凭据安全存储与"自行进入配置"

**三层凭据架构**：

```
① 加密存储    本地 Vault（SQLite/文件 + AES-GCM，密钥由主口令 KDF 派生）
              ↑ 或用 DSH credentials seam 的 file 层（$DSH_HOME/.credentials.yaml）
② 引用注入    所有配置/代码/Git 仓里只有「引用名」如 VAULT://home/cam-tapo-177
              （DSH credentials seam 的既定语义：空值视为不存在，每次操作重新解析 → 支持轮换不重启）
③ 凭据代理    CredentialBroker.execute(target, action, params)
              · 模型/工作流只能提交「意图」，永远拿不到明文
              · Broker 在内存中完成认证、执行、脱敏日志
              · 每次调用写审计：who/when/target/action/result
```

**"自行进入配置"的能力分级**：

| 级别 | 行为 | 授权要求 |
|---|---|---|
| 自动只读 | 定时采集配置、快照、比对 | 一次性授权范围即可长期运行 |
| 半自动写 | 产品生成变更方案 + 一键执行，人工点确认 | 逐次审批 + 变更窗口 |
| 委托写 | 客户授权后产品自动执行低风险变更（改码率、重启 IoT） | 白名单 + 审批 + 自动回滚点 |
| **禁止** | 远程开门、防火墙放行、恢复出厂、改 WAN | **永久人工执行**，产品只给引导 |

**适配器优先级**（主路由 / NVR / CCTV / AP / 交换机 / 防火墙）：

| 目标 | 首选协议 | 只读 | 写 |
|---|---|---|---|
| 主路由（消费级/云托管） | 厂商云 API；本地 Web 兜底 | ✅ | ⚠️ 常被云托管锁定（本次 Comcast 网关信道只读就是实例） |
| 交换机（可管理） | SNMP + SSH | ✅ 端口/MAC/错误 | ✅ VLAN/端口开关（高危需审批） |
| AP / 无线控制器 | 厂商 API（Omada/UniFi/Aruba/H3C）、SNMP | ✅ 关联表/信道/功率 | ✅ 信道/功率/SSID |
| NVR | 海康 ISAPI / 大华 / ONVIF | ✅ 通道/硬盘/录像计划 | ✅ 录像计划/重启 |
| CCTV | ONVIF(Profile S/T) + 厂商 API | ✅ 码流/编码参数 | ✅ 码率/帧率/OSD |
| 门禁 | 厂商 HTTP/SDK | ✅ 在线/事件 | ⚠️ 权限/时段；**开门禁止** |
| 防火墙 | SSH/HTTPS 只读 | ✅ 策略/NAT/会话数 | ❌ 默认禁止，只出建议 |

## 5. IOC 与 3D 可视化（需求 4）

### 5.1 3D 场景的务实路线

**不做数字孪生动画，做"可定位的 3D"**——第一版目标是"设备在哪、连到哪、健康如何"，不是建筑渲染。

| 阶段 | 内容 | 成本 |
|---|---|---|
| V1 | 楼层等轴图 + 设备图标（按角色换模型）+ 链路连线 + 状态着色 | 低 |
| V2 | glTF 机柜/机房模型 + U 位摆放 + 真实拓扑走向 | 中 |
| V3 | 天线覆盖热力（基于 AP 位置 + 实测 RSSI 插值）+ 信道干扰可视化 | 中高 |
| V4 | 业务流动画（CCTV→NVR→客户端） | 高（按需） |

**技术选型**：React Three Fiber（`@react-three/fiber` + `drei`）+ glTF + instancing（几百个摄像头/面板同屏）。低端设备自动降级为 2D SVG 拓扑。

**驱动数据**：`location` 元数据（floor / room / rack / u / x / y）+ 拓扑图。**自动布局 + 人工拖拽修正**，拖拽结果回写 Git。

### 5.2 图层（同一份数据，多视角）

物理层（设备/链路）· 逻辑层（IP/VLAN/路由）· 无线层（信道热力/干扰）· 业务层（CCTV/门禁/IoT 分组）· 安全层（暴露面/弱口令/Rogue AP）。

### 5.3 IOC 大屏

一屏呈现：**资产健康（L0-L3 分布）· 体验分（五域）· 实时告警 · 变更审计 · 摄像头在线率 · 无线拥塞热力**。
点击任意元素 → 侧栏唤起 Chat："这台为什么卡？"

> 若你说的 IOC 是安全侧的 **IoC（失陷指标）**：架构中同一位置预留 `threat-intel` 适配器（吃 STIX/TAXII、DNS 黑名单、C2 特征），与拓扑数据联查"哪些内网设备在与失陷域名通信"。两种理解共用同一可视化管线，不冲突。

## 6. Web 应用与内嵌 Harness Chat（需求 5、7）

### 6.1 前端功能页

`拓扑` · `3D/IOC` · `资产台账` · `质量看板` · `配置与手册` · `GitOps` · `报告` · `告警` · `运维台` · `设置`

### 6.2 每个功能页内嵌 Chat（需求 7 的关键）

用 DSH 的 **Client Slot 机制**把会话面板挂进每个页面，四种能力：

| 能力 | 实现 |
|---|---|
| **上下文注入** | 当前页面实体（选中的设备/链路/Finding/报告）作为会话上下文，用户不用重复描述 |
| **工具作用域** | 每页只暴露该页授权工具（拓扑页可改设备类型；配置页可发起变更；报告页只能读）——**从机制上防止越权** |
| **双向联动** | Chat 改页面状态（"把 .204 标成 AP"）；页面操作生成 Chat 提示词（点告警 →"分析这个"） |
| **三种模式** | `答疑`（问什么答什么）/ `纠错`（针对当前数据修正）/ `培训`（带步骤引导 + 检查点） |

### 6.3 培训模式（需求 7 的"培训客户使用"）

把 Runbook 变成**交互式引导**：

```
Chat：现在请打开浏览器访问 http://10.0.0.204 ，使用 admin 账号登录。
用户：（操作）
Chat：登录成功了吗？
用户：好了
Chat：请进入「无线设置 → 2.4G → 信道」，截图或告诉我当前值。
      → 探针同时复测确认改动生效（不依赖用户自述）
```

**检查点由探针验证，不采信口头确认**——这是把"培训"变成"可验证培训"的关键。

## 7. 数据与存储（需求 5：TD + MQTT + PG）

| 存储 | 承载 | 为什么是它 |
|---|---|---|
| **PostgreSQL** | 资产、拓扑、配置快照、Runbook、工单、审计、用户权限 | 强关系 + 事务 + JSONB 灵活性 |
| **TDengine** | 探针采样、空口指标、体验分时序 | 超表按 `node_id` 建标签，压缩率高、聚合快，ARM64 友好 |
| **MQTT (EMQX)** | 探针→平台→执行器事件、告警、外部集成 | 解耦与断线续传；QoS 1 |
| 文件/对象 | 抓包 pcap、报告 PDF、3D 模型、知识库附件 | 不进库，按保留策略清理 |

**TDengine 超表设计（示例）**：

```sql
CREATE STABLE metric (
  ts TIMESTAMP, value DOUBLE
) TAGS (
  site BINARY(64), node_id BINARY(64), metric BINARY(64), unit BINARY(16)
);
-- 保留：原始 30 天，1 分钟降采样 1 年，1 小时降采样 3 年
```

**MQTT 主题设计**：

```
netops/{site}/probe/{probe_id}/fact        # 探针上报事实
netops/{site}/event/finding                # 生成的发现
netops/{site}/cmd/{adapter}/{target}       # 执行器指令（需审批令牌）
netops/{site}/report/{period}              # 报告完成通知
```

**容量估算**（给客户算账用）：

```
每秒指标点数 = 设备数 × 每设备指标数 ÷ 采集间隔
例：30 设备 × 20 指标 ÷ 300s ≈ 2 点/秒 → 每天约 17 万点
TDengine 单点压缩后 < 1 字节量级 → 一年 < 100 MB（不含降采样前的原始）
```

结论：**时序不是瓶颈，抓包和报告附件才是**。抓包默认只保留异常时段。

## 8. GitHub 配置仓库（需求 6）

### 8.1 组织与命名

```
github.com/<org>/netops-customers/          # 或每客户一仓（推荐每客户一仓，权限隔离更好）
└── <customer-slug>/                        # 私有仓库
```

### 8.2 仓库结构（模板见 `customer-repo-template/`）

```
├── topology/
│   └── desired.yml            期望拓扑：链路、归属、位置坐标
├── policies/
│   ├── scan-scope.yml         授权扫描范围（含授权书编号与有效期）

    └── 2026-09-10-daily.md
```

### 8.3 什么进仓、什么绝不进仓

| 进仓 | 不进仓 |
|---|---|
| 拓扑期望态、台账、策略 | **明文凭据**（只放引用名） |
| Runbook、报告 | 抓包原文（含隐私） |
| 变更记录（PR 即审计） | 客户个人数据 |

若客户坚持密码必须入库：用 **SOPS + age**，`.sops.yaml` 声明加密规则，CI 校验"任何文件不得出现明文凭据"。**默认方案仍是引用名 + 本地 Vault**。

### 8.4 GitOps 变更流

```
UI 上的一次修正/变更
  → 生成本地 diff
    → 提交分支 + 开 PR（自动附带：影响面分析、回滚方案、证据链接）
      → 客户/我方审批（GitHub Review 或产品内审批）
        → 合并
          → 一体机轮询/Webhook 收到 → 热加载生效
            → 探针复测 → 结果回写 PR 评论
```

**离线容错**：断网时本地缓存继续采集与执行已批准任务，恢复后补 PR 与同步；冲突以"人工裁决"兜底，绝不自动强推。

> **合规备选**：部分客户不允许配置出到公网 GitHub → 同一套 GitOps 用自托管 **Gitea/Forgejo**，产品里只切换 remote 地址。

## 9. 报告与故障分析（需求 8）

### 9.1 报告矩阵

| 报告 | 周期 | 内容 | 交付 |
|---|---|---|---|
| **日报** | 每日 07:00 | 可用性、新告警、变更记录、五域体验分、异常设备 | Web / PDF / 邮件 / 企微钉钉 Slack |
| **周报** | 每周一 | 趋势曲线、基线偏离、Top 问题排名、优化建议、容量预测 | 同上 |
| **事件报告（RCA）** | 触发式 | 时间线、证据链、影响面、根因、处置、验证结果 | Web / 导出 |
| **月度资产健康** | 每月 | L0-L3 分布变化、暴露面、固件过期、凭据合规 | 同上 |

### 9.2 报告引擎原则

**确定性数据渲染 + LLM 只润色叙述**。所有数字、图表、证据链接由模板引擎从 PG/TD 生成；LLM 只负责：
- 把多项指标关联成"可能的根因"
- 生成人类可读的叙述与优先级排序
- 把处置建议转成可执行的 Runbook 步骤或 PR 草稿

**每条结论必须带 `evidence[]` 指回原始采样/快照**，否则不予展示（可审计性）。

### 9.3 RCA 报告模板

```
1. 摘要（一句话根因 + 影响面 + 建议）        ← LLM
2. 时间线（首次异常 → 告警 → 处置 → 恢复）    ← 数据
3. 证据链（指标曲线、配置 diff、日志摘录）    ← 数据
4. 根因分析（含排除项与置信度）              ← LLM + 证据引用
5. 影响面（哪些 CCTV/门禁/IoT 受影响，时长）  ← 数据
6. 处置建议（分优先级，标注风险与回滚）       ← LLM + Runbook
7. 验证结果（复测前后的指标对比）            ← 数据
```

### 10.1 服务清单（Docker Compose 见 `deploy/`）

| 服务 | 镜像 | 作用 | 网络 |
|---|---|---|---|
| `probe` | 自研 | 采集（host 网络 + NET_RAW/NET_ADMIN） | **host** |
| `api` | 自研 | 业务后端 + API Gateway | bridge |
| `web` | 自研 | 前端 + 内嵌 Chat | bridge |
| `agent` | DSH profile | Harness（会话/工具/审批） | bridge |
| `postgres` | postgres:16-alpine | 主数据 | bridge |
| `tdengine` | tdengine/tdengine:3 | 时序 | bridge |
| `mqtt` | emqx/emqx (或 mosquitto:2) | 事件总线 | bridge |
| `worker` | 自研 | 报告/任务调度/适配器执行 | bridge |
| `gitea`（可选） | gitea/gitea | 客户不允许公网 Git 时 | bridge |

### 10.2 硬件选型与容量真相

| 场景 | 配置 | 结论 |
|---|---|---|
| **推荐** | 树莓派 5 / 8GB + **NVMe SSD**（不要用 SD 卡！） | 全栈紧凑模式可跑（TD+PG+MQTT+Web+Probe ≈ 2–3 GB） |
| 边缘 | 树莓派 4 / 4GB | 需关闭 TD 历史降采样、报告延后生成 |
| 稳妥 | x86 迷你主机（N100/16GB） | 客户设备多、要本地抓包分析时选它 |
| **分离式** | 探针盒（Pi）+ 中央服务器 | 多站点/多客户，MSP 场景 |

> **纠正（本文档上一版此处表述错误）**：推理全在外部 API，但这**不等于**"本机瓶颈只在探针和 DB"。真正先出事的是**内存**，而**时序 DB 的吞吐根本不是瓶颈**。

| 负载 | 量级估算（Pi 5，30–200 设备） | 属性 |
|---|---|---|
| 时序写入 | 30 设备 × 20 指标 / 300s ≈ **2 点/秒**；200 设备 60s 也就 ~170 点/秒 | 可忽略（TDengine 单机可百万点/秒） |
| 关系库读写 | 每轮扫描几十~几百次查询 | 可忽略 |
| **Agent 会话** | **每会话 ≈ 1 GiB 起**（官方起点），随会话长度与工具活动增长 | **内存 ← 第一个撞墙** |
| Harness 单轮 | 上下文组装 + 工具结果 JSON 解析，可阻塞事件循环 | 延迟 / 并发 |
| 探针扫描 | /24 + `nmap -sV` ≈ 单核 30–120 s | CPU 突发 |
| RTSP 抽样 | 每路 2–8 Mbps，10 路并发 = 20–80 Mbps | 网络突发 |
| 抓包 | 千兆线速 ≈ 120 MB/s，几分钟写满盘 | **IO 突发，必须限流** |
| 外网 API | RTT 1–10 s，egress 0.1–1 MB/轮 | 体感延迟，几乎不吃本机资源 |

**正确排序：内存 > 磁盘耐久与 IO 尖峰 > 探针突发对同机服务的影响 > harness 事件循环 > 外网 RTT > DB 吞吐。**

> 上一版把"DB 写不进去 / 查得慢"说成吞吐问题 —— 那其实是 **SD 卡耐久性与写入尖峰**问题，属于 DB 话题但不是吞吐话题，我混成了一句话。

**那一体机上为什么还要本地库？** 三个理由，且都不是吞吐：① **断网可用** —— 客户网络出问题时往往外网也不通，诊断不能停；② **隐私与带宽** —— 原始指标不出客户网络；③ **缓冲** —— 外网恢复后补传。

**不想要就分离部署**：

- **形态 A 单机**：Pi 5 8GB + NVMe 全栈。内存预算 ≈ OS 0.5G + Docker 0.2G + TDengine 0.3–0.5G + PG 0.2–0.4G + EMQX 0.15–0.3G + **Agent 会话 N × ~1 GB** + 探针 0.1–0.5G。
  - Anthropic 对 Agent SDK 的官方起点是 **1 GiB RAM / 1 CPU / 5 GiB disk per agent**，且"随会话长度与工具活动增长，要按你实际需要的会话长度与并发来配，而不是按空闲基线"。
  - 扣掉 OS/Docker/DB/探针 ≈ 1.5–2 GB，Pi 5 8GB 留给 Agent 的约 5–6 GB → **并发 agent 会话上限约 2–4 个，且偏乐观**。
  - **结论：Pi 上必须串行化** —— 交互 chat 常驻 1 个会话；批量任务（日报、归因、报告）由队列**一次跑 1 个**。**不要设计成十来个前端页面各自开一个长驻会话。**
- **形态 B 探针盒 + 中央**（多站点 / MSP 推荐）：Pi 上只留 探针 + MQTT + 本地落盘缓冲 + 极简只读页；PG / TD / Web / Agent 全部集中到 x86 或服务器，按 `(主机内存 - 开销) / 单会话内存上限` 算并发，多实例时用 `sessionId` 一致性哈希把同一会话钉在同一实例。

**选型口诀：单客户单站点 → 形态 A（且严格串行）；多站点/多客户/要 AI 集中 → 形态 B。**

若客户要求**完全离线推理**：必须换 x86 + 本地小模型，且根因分析质量下降、成本结构改变 —— 售前讲清。

### 10.3 首次接入流程（现场 15 分钟）

```
1. 接网线开机 → 一体机起一个本地 AP/热点或固定 IP（默认 192.168.88.1）
2. 管理员连上去，打开 Web 向导
3. 【授权】勾选授权范围（网段白名单）+ 上传/签署授权确认 → 落 policies/scan-scope.yml
4. 【自检】探针跑能力自检（出口接口/权限/无线/网关托管）→ 展示结果与能力边界
5. 【发现】全网段扫描（首次 5–15 分钟，视规模）→ 产出候选事实
6. 【确认】人工在 UI 上确认/修正设备类型与链路（低置信度优先）
7. 【深度】按需录入关键设备凭据（Vault）→ 升级 L1→L2
8. 【基线】连续采集 24–72 小时建立基线
9. 【首报】生成《网络体检报告》+ 初始化客户 Git 仓并推送首次 commit
```

### 10.4 升级、备份与远程运维

- **升级**：镜像 tag 固定 + `docker compose pull && up -d`；DB schema 用 migration 工具，升级前自动备份。
- **备份**：PG `pg_dump` 每日 + TD 保留策略 + Git 仓本身即配置备份 → 打包成加密归档。
- **远程运维**：默认不开；需要时走客户侧反向隧道（客户可控开关），并全程审计。

## 11. 安全与合规

1. **书面授权 + 扫描范围白名单**：`policies/scan-scope.yml` 带授权书编号与有效期，到期自动停止主动扫描。
2. **默认只读**；写操作走审批（DSH `permission-presets` + `user-approval`）。
3. **凭据代理**：模型与日志永不接触明文；支持轮换（DSH credentials 每次操作重新解析，无需重启）。
4. **审计不可抵赖**：所有采集/读取/变更写 `audit` 表 + Git 历史双记录。
5. **数据本地化**：默认全本地；云托管模式只上报指标与拓扑，**不上传抓包**。
6. **Runbook 免责与版本**：每份手册标注适用固件与验证状态；过期固件上自动降级为 `draft` 并提示。
7. **高风险禁令**：远程开门、防火墙放行、恢复出厂、改 WAN —— 产品不提供自动执行路径。

## 12. 路线图

| 阶段 | 周期 | 交付 | 验收标准 |
|---|---|---|---|
| **P0 能看见** | 3–4 周 | 探针（自检+发现+指纹）+ PG/TD/MQTT 落库 + 首份体检报告 | 接入陌生网络 30 分钟内出报告，能复现本次会话的全部结论 |
| **P1 能管住** | 4–8 周 | 拓扑图 + 设备卡片 + 凭据代理 + Runbook 引擎（先 20 个主流型号）+ L0-L3 分级 | 关键设备升到 L2；配置快照与差分可用 |
| **P2 能看懂** | 8–14 周 | 3D/IOC + 五域质量看板 + 内嵌 Chat（含培训模式）+ GitOps 仓库 | 客户能自己看懂并在 Chat 引导下完成一次真实配置 |
| **P3 能闭环** | 14–24 周 | 受控变更（审批→执行→复测）+ 日报周报 + RCA + 告警 | 至少一类设备（AP 信道 / CCTV 码率）实现自动闭环 |
| **P4 规模化** | 24 周+ | 多站点多租户 + MSP 控制台 + 开放 API + 门禁/IoT 深适配 | 单平台管 50+ 站点 |

**P0 就能卖**：把本次会话的全部诊断能力产品化成"插上就出报告"，已是可交付的最小单元。

## 13. 风险与取舍（必须在立项时拍板）

| 风险 | 影响 | 对策 |
|---|---|---|
| **厂商 API 碎片化**（最大风险） | 适配器做不完 | 适配器 + **人工兜底**双轨；用 Runbook 覆盖长尾；优先做覆盖率最高的 20 个型号 |
| 网关被云托管（本次 Comcast 实例） | 改不了信道 | 能力降级要**如实上报**；引导客户改用可控 AP 或 Bridge 模式 |
| 3D 是成本黑洞 | 拖垮进度 | V1 只做"可定位的 3D"，不做渲染动画；低端机降级 2D |
| Runbook 生成被 LLM 幻觉污染 | 生产事故 | 策展 + 真机验证 + 版本标记，LLM 只做检索与裁剪 |
| GitHub 托管客户配置的合规问题 | 客户拒签 | 自托管 Gitea 同构方案，一行配置切换 |
| 工具许可证（nmap/arp-scan 等） | 分发风险 | 立项即审计；必要时替换为自研实现 |
| 树莓派 SD 卡寿命 | 数据损坏 | 强制 NVMe/USB SSD；DB 目录独立挂载 |
| 凭据集中存储成为攻击目标 | 灾难性 | 本地加密 + 主口令不落盘 + 最小权限 + 全审计；禁开门类高危自动化 |

## 附录：DSH 侧落地要点（承接上一版）

- 产品能力必须是 **package + composition row**，不能是动态插件（进程重启即消失）。
- 常驻：`dsh --profile netops --patch deploy/overlay/svc.yml`
- 周期采集：`dsh --profile headless --patch deploy/overlay/probe.yml "<task>"`，由容器内 cron / systemd timer 驱动。
- **不要用 `dsh-schedule` 做产品调度**：它只在 live 会话内交付、最小间隔 5 分钟、不支持 cron。
- 校验组合：`dsh --profile netops --dump-config`
